## DLT and captures (built)

DLT import was the focus from 2026-10-18 (owner); `.dlt` files, pcap / pcapng and MF4 are read now. The search manager came next and is built too (below). Design of the layers: `sources-and-signals.md`.

Decided for DLT: own zero-copy parser in `core/src/input/dlt/` (no crate, no dependency); synthetic test data only (a DLT writer + `gen_dlt` example); shown as a **table with aligned, resizable columns** in our own view (no column sorting; each row is still one tab-separated text line, so search, highlight and copy keep working).

Done (step 1): `LogSource::line_bytes` returns `Cow`; sources can supply a field schema, per-line field values and levels; `Event` is lazy over `(source, line)`, so header-only filters never render a line; the DSL accepts source fields (`apid == NAV`, `mcnt >= 0x10`), resolved by `Query::bind` / `compile_for`. Text-log benchmark unchanged (1 GiB: `search ERROR` ~30 ms, `level >= ERROR` ~31 ms).

Done (step 2): own DLT reader in `core/src/input/dlt/` (no new dependencies). `nerka_core::open` picks DLT or text by content (the GUI too, since step 3).
- Index = one `u64` offset per message (~8 B/msg). Headers are read in place, so header-only filters never decode payloads.
- Fields: `ecu apid ctid type mcnt tmsp seid mid mode payload`; `payload` is the decoded payload column only (unlike `raw`, which spans every column), e.g. `payload ~ "timeout"`, and is checked after the header conditions; `mode` is `verbose` / `non-verbose` (`mid` stays empty on verbose messages, since 0 is a valid message id); `level` comes from the header (`VERBOSE` is accepted as an alias for `TRACE`).
- Line = tab-separated columns `time tmsp ecu apid ctid type payload` (time is the storage time in **local time or UTC**, see "Times: local or UTC"; `type` is the level for log messages, e.g. `error`).
- Payload: verbose bool/int/float/string/raw/trace info, with VARI names and units; arrays, structs and fixed-point fall back to `<undecoded> hex`. Non-verbose: `[id] hex`. Control: service name, status, version string.
- Corrupt data: resync on the next `DLT\x01`, skipped bytes counted. Files without storage headers aren't supported.
- `writer` module + `examples/gen_dlt.rs` produce synthetic files.
- 1 GiB synthetic DLT (12.5M messages): index 280 ms (single-threaded), 95 MiB; `ecu == ECU1` 37 ms, `apid == NAV AND level >= WARN` 29 ms, `level >= ERROR` 32 ms, `raw ~ /timeout/` 288 ms (renders every line), `apid == NAV AND raw ~ /timeout/` 60 ms.

Done (step 3): the GUI opens files via `nerka_core::open`; sources with columns (`LogSource::columns`, DLT) are shown as a **table** in the existing view: a header row with the column names, cells aligned at column boundaries, faint dividers, and a divider drag in the header resizes the column (widths belong to the tab, shared by the main and filter views; not saved yet). Text that doesn't fit a cell is hidden and marked with "…". Selection, double-click, search highlighting and copy still work on the line text (copy keeps the tabs, so it pastes into a spreadsheet as columns). Plain text looks as before. The Open dialog lists `.dlt` files.

Done (step 4, 2026-10-20): **DLT in pcap / pcapng captures**, read in place (no temporary `.dlt`): `core/src/input/capture/` (container `pcap.rs`: pcap µs/ns both byte orders, pcapng sections / interfaces / `if_tsresol` / `if_tsoffset`; transport `net.rs`: Ethernet, stacked VLAN tags, Linux SLL / SLL2, raw IP, loopback, IPv4 / IPv6 with **fragment reassembly** in any order (30 s capture-time timeout, at most 4096 pending); router: UDP destination ports, default **3490** only (the DLT protocol's port; owner, 2026-10-20), configurable: CLI `--dlt-port` (repeatable), GUI ⚙ → UDP ports (saved in `prefs` as `dlt_ports`, used for captures opened afterwards), core `OpenOptions` / `CaptureOptions`). The DLT reader was generalised: a message takes its storage time and ECU from its index entry (`Framed`, 16 B: offset with a side-buffer bit and a 15-bit capture channel, time), so a `.dlt` file is the simplest case; reassembled datagrams live in a side buffer. A message gets the time of the frame that completed its datagram; its ECU is its own (WEID). `nerka_core::open` recognises captures by content; the GUI's Open dialog lists `.pcap` / `.pcapng`. No new dependency. Benchmark: `big.dlt` → `big.pcap` with `examples/dlt_to_pcap` (870 MB, 12.5 M messages, VLAN, several messages per datagram, every 400th datagram fragmented): index ~300 ms (`.dlt`: ~255 ms), the same match counts and search times as the `.dlt`; the `.dlt` numbers are unchanged by the refactor. **MF4** (2026-10-20, `capture/mf4.rs`, own reader, no dependency): block tree over the mapped file; unsorted (1/2/4/8-byte record ids) and sorted data; DT / DL / HL (records spanning data blocks are copied to the side buffer); VLSD channel groups (paired with their frame group by order) and SD blocks (by offset); **Compressed data** (DZ blocks, deflate, transposed or not; 2026-10-26, `capture/unpack.rs`, dependency `miniz_oxide`): unpacked once, as a stream, into a file in the **unpack cache** (`%LOCALAPPDATA%\nerka\cache`, `~/.cache/nerka`), which is mapped like any log — RAM doesn't grow with the number of tabs, and the reader stays zero-copy (owner, 2026-10-26: unpacking into memory would fill RAM with several tabs). The block tree is read from the original file, the records from the cache file (every data block, unpacked or copied, in the order the tree reaches them; `Layout` maps a block to its place). The cache file is named after the original's path, size and modification time, so opening the file again maps it without unpacking; written to a temporary name and renamed (two tabs or instances can open the same file). The cache keeps under a limit (default 8 GiB; GUI ⚙ → Compressed MF4: size limit, usage, Clear) by removing the least recently used files after writing one (an open one stays on Windows). CLI `--unpack-dir DIR`; without a cache folder (core's default, tests) the data is unpacked into memory. Not yet: keeping only the DLT bytes while unpacking (would make the cache smaller when the log has other traffic); `.gz` / `.zst` captures (same approach). Benchmark (1 GiB `big.dlt` → `examples/dlt_to_mf4`, 12.5 M messages, release, Windows): uncompressed MF4 index 1.35 s before, 1.33 s after, search ~29 ms either way; deflated in 4 MiB DZ blocks (264 MB): first open 2.9 s (unpacking), then 1.33 s from the cache; one DZ block for all records and one for all signal data: 2.9 s, then 0.85 s (a cold cache file read from disk: ~3 s); search ~29 ms in every case. Groups by channel names (`ETH_Frame.*` → Ethernet frames into the same transport and port router as pcap; `DLT_Frame.*` → DLT directly, its `ECU_ID` the fallback ECU), else by shape (an Ethernet bus-event group, as X2E loggers write). Time = header start + master channel through its linear conversion (none: the raw value in seconds, as the spec says). Not yet tried on real-world files (own or public). Layers: `sources-and-signals.md`.

Open with the owner: save column widths? Sorting stays out (decided).

### DLT decisions (owner, 2026-10-18)

- **Own parser, no crate** (spec §3.1: few dependencies). Zero-copy over the mmap.
- **Location:** `core/src/input/dlt/`, not a `nerka-dlt` crate yet. Extract it into a crate when the `Container` / `Decoder` traits of `sources-and-signals.md` arrive with pcap; that's where a crate boundary pays off.
- **Filtering** by ECU / APID / CTID / level comes from the headers (source-supplied fields + DSL field predicates), never guessed from text. Header-only filters must not decode payloads, and every fast path is tested against the naive per-line evaluator.
- **Display:** a real table (aligned, resizable columns), built into our own log view; **no column sorting** (it would break line numbers, bookmarks and next/previous match, and logs are read in time order). Each row is still one tab-separated text line underneath.
- **Test data:** synthetic only (`writer` module + `gen_dlt`); no real `.dlt` files in the repo.
- **Non-verbose messages:** shown as `[message id] hex` until FIBEX support exists. `mid` is that message id: the key into the FIBEX database that will later decode the payload.
- **Time:** `time` is the logger's storage time (seconds since the epoch, UTC), rendered in local time or UTC, `tmsp` the ECU uptime (0.1 ms).
- **Times: local or UTC (owner, 2026-10-26):** values stay UTC inside; what is shown and typed is **local time by default in the GUI** (as DLT Viewer and Wireshark show it; Settings → Times → Show: Local time / UTC, pref `local_time`), UTC by default in the CLI (`--local-time`; stable output for scripts). One switch, `nerka_core::time::set_local`, covers DLT's `time` column, `format_time` (signals, line window, plot axis, rounded to local hours) and `parse_time`: a date-time without a zone (a plain-text capture, `@time >= "…"`) is read as local time, so text logs show as written either way; a time of day is never converted. The offset at each instant comes from the OS with its DST rules for that date (`localtime_r` on Unix, `SystemTimeToTzSpecificLocalTimeEx` on Windows; no dependency), cached per quarter hour. Changing it reopens the tabs. Cost on a 512 MiB DLT filter that renders every line: 177 ms before, 183–188 ms UTC, 186–208 ms local.
- **MF4 local start time (owner, 2026-10-26, optional):** an MF4 header whose time flag says "local time" (`hd_time_flags` bit 0) is read in this computer's zone (Settings → Times → MF4, pref `mf4_local_time`, default on; CLI `--mf4-utc` turns it off); without the flag the start time is UTC, as the format says. The header's timezone / DST offsets are not used. The full `Timestamp { ns, clock }` model of `sources-and-signals.md` waits until sources are merged or signals arrive.

## Signals (v1 built: core, CLI, GUI)

What a signal is was agreed with the owner on 2026-10-24: `sources-and-signals.md` → "What a signal is". Built (2026-10-24):

- **Core** (`core/src/signal.rs`): a `SignalDef` is a name, a kind (`num`: the capture read as decimal / float / `0x` hex; `enum`: the captured text), an NFD query and the named regex group to take the value from (default: the signal's name). A row carries the value when the whole query matches and the group captured something (from a raw regex or a field regex such as `payload ~ /…/`). A signal can't use other signals. `Signals` is a tab's set, by unique name. Spec line (CLI): `NAME[(GROUP)][:num|enum]=QUERY`.
- **NFD** (owner: the syntax keeps signals apart from source fields): `@speed > 100`, `@gear == D`, `@gear ~ /D|N/`. **Events and states** (owner, 2026-10-24): a row that carries a value is an *event*; the *state* is the value held from an event until the next one (already the new value on the event row; none before the first event; not carried from one file into the next in a view of several). `@x` / `@x.state` is the state, `@x.event` a value received on the row, `@x.changed` an event that changed the state (the first one too); `.event` and `.changed` also stand alone. `Query::with_signals` / `compile_in` resolve them; a row without a value only satisfies `!=` and `!~`; unknown signals and views, and operators that don't fit the kind, are errors with positions. The engine collects a signal's events once per file (`SignalDef::series`, cached with the definition and shared by its copies; `Query::prepare` before a scan), so each row only looks them up (binary search). An event condition that rows without an event fail lends its signal's regex as the prefilter. Fast vs naive path tested as for every engine change, also on a view of several files.
- **CLI:** `--signal SPEC` (global, repeatable): `nerka --signal 'lat=/latency_us=(?<lat>\d+)/' filter '@lat > 9000' app.log`.
- **GUI:** 📈 **Signals** in the toolbar opens a right panel for the active tab: each signal with its kind and its state on the cursor line — `• event` when the line itself carries it, else `↑ N`, the line of the event that set it (click to go there); — before the first event; … while the events are being collected (a background job after a change or load); "error" with the reason on hover when its query doesn't fit the file — ✎ edit, − remove, and a form (name, kind, group, query) to add one. Both boxes (Auto and NFD) and library queries know the tab's signals; editing them re-runs a filter or search that uses `@`. `nerka-gui app.log --signal SPEC` defines them at startup. Signals are per tab and not saved (not in presets, not carried by Move to new window).
- **Benchmark** (1 GiB, release, Windows): existing queries unchanged (`search ERROR` ~29–31 ms, `level >= WARN AND raw ~ /timeout/` ~30 ms; DLT `apid == NAV AND level >= WARN` ~30 ms). One CLI run, the pass that collects the events included: `--signal 'lat=/latency_us=(?<lat>\d+)/'` (2 M events) `@lat > 9000` ~110 ms, `@lat.event > 9000` ~115 ms; a timestamp on every line as the clock, `--signal 't:time=/^(?<t>\S+ \S+)/'` (12 M events) `@t < "00:00:30" AND level >= ERROR` ~0.5 s; DLT `@time < "00:01:00"` ~26 ms (no pass: the source answers). Collecting events: a signal that is only a regex scans for it as a plain regex and captures once per hit without allocating; numbers go straight into arrays (with rayon's `flatten` over `Option`s it took 1.7 s, then 4.5 s).
- **Time** (2026-10-24, owner: time is a signal): kind `time` (values in seconds since the epoch, UTC, `core/src/time.rs`): a capture read as a date-time, a time of day (a day is added when it goes back by more than 12 h, i.e. at midnight) or a number. **Formats (owner, 2026-11-02: it was too strict):** dates `2025-10-17`, `2025/10/17`, `2025.10.17`, `17.10.2025`, compact `20251017T100001`, month names (`17 Oct 2025`, `Oct 17, 2025`, `17-Oct-2025`, Apache's `17/Oct/2025:10:00:01 +0200`, a weekday first, RFC 2822, `Fri Oct 17 10:00:01 2025`); times `10:00:01`, `9:05:01`, `10:00`, a fraction after `.` or `,` (log4j), `AM` / `PM`; zones `Z`, `UTC`, `GMT`, `±hh:mm`, `±hhmm`, `±hh`; plain numbers as seconds, or ms / µs / ns since the epoch when too large for seconds (`core/src/time.rs`, `parse_time`, hand-written: a value per event, the time-signal benchmark is unchanged). Dates without a year (BSD syslog `Oct 17 10:00:01`, `17 Oct 10:00:01`) are this year's (owner, 2026-11-02); a weekday before a date must be a weekday's name. Not read, ambiguous (to decide with the owner): slashed dates with the year last (`10/17/2025` or `17/10/2025`); and a pure 8-digit number stays seconds, not a compact date. `LogSource::time` gives a source's own time: DLT's storage (receive) time; a tab on such a file gets the built-in **`@time`** (every line an event; `Signals::for_source`, CLI and GUI). NFD compares times with a quoted date-time or time of day (`@time >= "2026-10-17 10:00:01.5"`, `@t < "10:30:00"` compares the time of day). The tab's **clock** (`Clock::of`) is the source's time, else its first `time` signal (its state at each line), else line numbers. Not supported yet: user-given formats, time zones other than in the text or this computer's (local time: "Times: local or UTC").
- **Plot** (2026-10-24, `ui/src/plot.rs`, drawn with egui's painter — `egui_plot` 0.38, the version for our egui, was 5 days old and lacks bands and lanes; no new dependency): a checkbox per signal in the Signals panel (not for `time` signals) plots it in a panel under the main view: one lane per signal on the clock's axis (time of day ticks; date in the hover), a number as its state (a step line, decimated to a step per pixel column), an enum as coloured bands with labels where wide enough; an **events** checkbox per lane ticks the lines where the value was received; the current line is a cursor; wheel zooms around the pointer, drag pans, double-click shows all, hover shows the value, a click goes to the nearest event. `nerka-gui --plot NAME` plots at startup. Without a clock the axis is line numbers (said above the lanes). **Many lanes (owner, 2026-10-25):** a lane is never lower than 52 points (its name, events box and y labels fit); lanes that don't fit scroll — a scrollbar at the right, or the wheel over the lane names (over the plot the wheel still zooms). Dragging the plot up and down scrolls through the lanes too, as left and right pans (owner, 2026-10-25). **Owner's feedback (2026-10-25):** the lane names' column is resizable (drag its edge; double-click: fit the longest name), names are cut to the width; lanes are reordered by dragging a lane's name (a line shows where it goes) or with Move up / down / to the top / to the bottom in the name's right-click menu, and keep their colour; the time axis labels show again (they were clipped with the scrolled lanes); cursors and bookmarks have a strip of their own above the lanes — their tags in a row (each cut where the next one in its row starts; hover: all of it; **stacked (owner, 2026-11-02: two bookmarks on one x looked like one):** a tag that would hide the name of the one before it, `🔖B1`, goes a row down, up to 4 rows, so bookmarks and cursors at the same or nearly the same x are one under the other, each with its name, hover and click; `stack_tags`), the Δt between neighbours on a row below them, just the time (the ends' names are on their tags; an end out of view is named, `‹ B2  10.000 s`) — so only their thin lines cross the values, and a bookmark's name and note are at the top like the cursors' names; the plot's 📷 copies *all* lanes, scrolling through them and putting the parts together (without the scrollbar; cursor and bookmark tags once). **↔ Fit** in the plot's header shows the whole x range again (as double-click does). Not yet: search / filter hits as markers on the axis, merging lanes, y zoom; the lanes are built in the UI thread once per change (not measured on millions of events).
- **Sources of signals (owner, 2026-10-24):** pack queries, signals the user defines, and later FIBEX / ARXML imports. A tab's signals are rebuilt (`Tab::refresh_signals`) from: the file's `@time`; the user's **saved signals** (every tab, `<config>/nerka/signals`, a spec line each, `Signals::to_text` / `parse_text`; written when the panel changes them; `--signal` at startup adds for the session); the **named groups of the selection's queries** with role Include or the new **Signal** role (`core::query_signals`; picked up from the selection without Apply). A group in several picked queries is one signal, their OR. A saved signal wins over a query one of the same name.
- **Signal role (owner):** a third role in the selection (`~`, `pack::Role::Signal`, `Selection::signal`, presets `node signal`): not in the filter (its text goes to `Expansion::aside`), gives signals, and can colour the lines it matches like an include. `nerka-gui --signal-pick ID` at startup.
- **Kinds of query signals (owner: inferred, overridable):** from the first values (up to 64 in the first 200 000 lines: all numbers → num, all times → time, else enum, `SignalDef::infer_kind`); a pack pins them with the query attribute `signals: t:time, v:num`; the panel's kind list overrides them for the tab.
- **Scope (owner: per signal; filters use only global ones):** each signal is `all` (events from every line) or `filtered` (only from the lines the filter keeps: the panel's state and the plot, `SignalSeries::within`, worked out once per filter result, `signals::Views`). A filter naming a `filtered` signal is an error. Spec lines carry it (`v:num:filtered=…`); the panel's all / filtered toggle switches it (saved signals: in the file; query signals: for the tab).
- **Menus with fields (fixed 2026-11-02, owner's report):** the plot's right-click menu (bookmark note) and a number lane's (marker labels and values, y range) closed when one of their fields was clicked, egui's context menus closing on any click; they close on a click outside, Esc or their buttons now (`FieldMenu::context_menu_with_fields`).
- **Plot:** "⧉ Own window" moves it into a separate OS window (a *deferred* egui viewport: it paints in a pass of its own, its state shared behind a mutex, `plot::Detached`; "⧉ Dock" returns it; closing it closes the plot, which opens there again: owner, 2026-11-12), titled `<window name> · Plot · <tab> — nerka`, showing the active tab. Right-click a number lane's name: y axis fits all values, fits the visible ones, or a fixed from / to. The header says what x is (`x: @t`, the file's time, line numbers); a `time` signal whose events are collected and empty (its regex doesn't fit the file) isn't the clock. `nerka-gui --plot-window` opens it at startup.
- **Markers and time cursors (owner, 2026-10-24):** *value markers* — right-click a number lane's name (the menu with its y axis): add, edit (value, label) or remove horizontal dashed lines at chosen values (limits, thresholds), labelled at the right; a fitted y axis widens to show them. *Time cursors* (owner: like a logic analyzer) — right-click in the plot: place cursor A, B, C… there, remove the nearest or all; drag a cursor line to move it (a drag elsewhere pans); between neighbours in time a bracket shows Δt (µs / ms / s / h m s, lines without a clock), and a line above the lanes lists each cursor's time and the Δts. Both per tab, this session. Startup: `--marker NAME=VALUE[:LABEL]`, `--cursor TIME`. The plot's help moved into a hover (ℹ) so its header row never gets wider than the panel.
- **Bookmarks as cursors (owner, 2026-10-24):** the tab's bookmarks are drawn in the plot as red lines at their line's time, with their note on a tag at the bottom (shortened; hover: all of it; click: go to the line); they take part in Δt like time cursors (named `🔖` and the bookmark's name) and in the summary line. A 🔖 checkbox in the plot's header shows or hides them. The plot's right-click menu bookmarks the event nearest to the click (any lane) with a note typed there (an existing bookmark's note is filled in and replaced); it is an ordinary bookmark, saved in the log's `.nerka-marks`.
- **Signals in the line window (owner, 2026-10-24):** the line window (Enter / Show whole line…) has a **Signals** section: first the signals the line carries (events), including every argument of a FIBEX-described message — also those not used as signals ("FIBEX, not used") — the tab's other signals with their state on the line and the line of the event that set it (click: go there; the window goes along) are folded away under "Held from earlier lines" (owner, 2026-10-25: show the line's own signals, not all of them). Each row says the kind and where the signal comes from (built in, saved, query, FIBEX). The values are worked out every frame, so they appear once background collection is done. The line window **follows the line selected** in the main view or the search hits (a click or the keys; owner), keeping Wrap. Everything under its buttons scrolls; ↑ / ↓ with the pointer over it (or a widget in it focused) step to the next / previous line of the view it follows — the search hits if it was opened or moved there, else the main view, which goes along (owner, 2026-10-26: arrows moved focus through the window's widgets). FIBEX 16/32-bit float arguments keep their own digits as values (20.79659, not the widened 20.79659080505371).
- **Crash on maximize (owner, 2026-10-24; fixed):** with the plot in its own window, maximizing a window crashed nerka (`0xc0000005` in `nvoglv64.dll`, NVIDIA's driver). eframe draws with wgpu, which picked **Vulkan** on Windows; reproduced with a script (maximize / restore while the pointer moves over the window). An immediate viewport crashed when the plot window was maximized; a deferred one fixed that, but maximizing the main window still crashed under Vulkan (2 runs in 3), never under **DirectX 12** (60+ cycles). So on Windows nerka asks wgpu for DirectX 12 (`wgpu_options` in `ui/src/main.rs`; `WGPU_BACKEND` still overrides); Linux and macOS keep wgpu's choice (Vulkan / Metal). No new dependency: wgpu was already eframe's renderer.
- **CPU with software rendering (owner, 2026-11-06):** in a VM without GPU access (Mesa llvmpipe / lavapipe, `DRI3 error` at start), hovering the signals cost 120–205 % CPU. Now it asks only when what the plot shows changed (`plot::WindowKey`: the plot's layout, cursors, zoom, the signals' generation, the file, the current line, the filter result, bookmarks, kept plots); the plot window repaints itself for its own input. Before/after numbers in the VM: to be measured. Next levers if still needed: fewer hover frames on a CPU adapter, less overdraw.
- **Numeric fields in a signal (2026-10-26):** `~` / `!~` work on numeric source fields too, on their decimal text, so a signal can capture one: `up_ecu1=ecu == ECU1 AND tmsp ~ /(?<up_ecu1>\d+)/` is ECU1's uptime (0.1 ms), whose drops are its resets. `tmsp` belongs to the ECU that sent the message, so it needs one signal per ECU; one signal split by a field automatically is not built.
- **Owner's feedback (2026-10-28):** lane names that don't fit keep their **end** (`…rear_right`): names often differ only there. **✖** at the right of the plot's header closes it (its lanes and settings are kept); **📈 Plot** in the Signals panel's header shows or hides it, and plotting a signal shows it. **Kept plots** (the owner asked to consider a plot library; `egui_plot` still lacks bands and lanes, so it is our own, no dependency): the list at the left of the plot's header switches between plots without building them again; a plot has **no name** until it is kept: ⋮ → Keep this plot as… (Keep: this session, `•`; Save: to disk); ⋮ → **New plot** starts a blank, unnamed plot without asking for a name (owner, 2026-10-28; a kept plot is kept as it is first, an unnamed one is replaced); Save '<name>' (overwrites its file; a saved plot changed since is marked `*`), Delete. ~~Switching keeps the current plot as it is in its entry first.~~ **A kept plot is a preset (owner, 2026-11-09: U5, reverses the line before):** it changes only on ⋮ → **Keep changes to '<name>'** (session plots) or **Save**; a tab's changes are its draft, marked `*`, kept per tab for the session when it switches away and shown again when it switches back; ⋮ → **Revert '<name>'** drops them; other tabs use the plot as kept (`ui/src/plots.rs`). A plot holds its lanes in order, each lane's events box, y axis and markers, the names' width and whether bookmarks show; not time cursors or the zoom (they belong to the file). Signals are named, so a plot can be used in another tab or file. **A lane whose signal the tab doesn't have stays in the plot** (owner, 2026-10-28: a plot kept in one tab came up empty in another; its lanes were dropped when that tab's signals were built again), named above the lanes ("Not in this tab: @w ✖"); if the loaded FIBEX files describe an argument of that name, a DLT tab picks it as a signal, as ticking it in the Signals panel does (`Tab::pick_plotted_arguments`). Files: `<config>/nerka/plots/<name>.nerka-plot` (format and parser: `core/src/plot.rs`).

## FIBEX (built: core, CLI, GUI)

Owner, 2026-10-24: FIBEX first (SOME/IP, if it comes, from ARXML); `quick-xml` approved; the first step decodes non-verbose messages from FIBEX files given for the session (the `nerka-db` intermediate format and a library of imports come later).

- **Reference:** open example FIBEX files for DLT non-verbose messages follow one convention; they aren't in the repo (our tests use hand-written FIBEX in the same convention). `NERKA_FIBEX_REF=<folder> cargo test -- --include-ignored` loads every file in a folder (the six tried: 19 messages, every argument type known).
- **Core** (`core/src/input/dlt/fibex.rs`, `Fibex`): a streaming read (`quick-xml`) of ECUS, FRAMES (`ID_<message id>`, PDU instances in sequence, `MANUFACTURER-EXTENSION`: type, level, APID, CTID, source file / line), PDUS (`ho:DESC` text, signal instances), SIGNALS → CODINGS (base data type, bit length); signals that aren't defined are read by their conventional names (`S_UINT32` …). Arguments: bool, 8–64-bit integers, 16/32/64-bit floats, length-prefixed strings and raw data, in the message's byte order. A file naming one ECU binds its frames to it; a lookup prefers the message's ECU, then unbound frames, then any, and the APID / CTID that match. Malformed XML is an error with the file and byte position.
- **DLT reader:** `OpenOptions::fibex` → `DltFile::with_fibex`. A described non-verbose payload is shown as text (pieces joined by a space; what can't be read follows as hex after `<undecoded>`); a message without extended header takes APID, CTID, type and level from its description (columns, `apid` / `ctid` / `type` fields, `level`), so filters and signals work on it. Undescribed messages stay `[id] hex`. Without FIBEX nothing changes.
- **CLI:** `--fibex FILE` (global, repeatable). **GUI:** a **FIBEX** section in the Signals panel (owner, 2026-10-24: FIBEX belongs with signals; it was a toolbar menu first): add files, see how many messages they describe and which files, forget them; for every tab, this session. DLT tabs read their files again with them, keeping filter, search, selection and the current line; `nerka-gui --fibex FILE` at startup.
- **Tried on an open example FIBEX** (owner's request; four messages, one ECU): a `.dlt` written to match it (no extended header, little and big endian) decodes as described — text, numbers next to text, both byte orders, APID / CTID / level filled in; an id it doesn't describe stays hex; header filters and a signal captured from the decoded text work.
- **Benchmark** (1 GiB `gen_dlt`, 12.5 M messages, release): `apid == NAV AND level >= WARN` ~29 ms with or without FIBEX; payload regexes 200–330 ms either way (run-to-run noise; 5 % of the messages are non-verbose there).
- **Arguments as signals (owner, 2026-10-24: list the embedded signals as a tree and plot them):** the FIBEX section of the Signals panel lists every typed argument of the described messages as a tree — ECU → APID / CTID → message (its template, `Free slots: <u16>`) → argument — with a filter box (small catalogs start unfolded). **Owner's tweaks (2026-10-28):** **Collapse all** / **Expand all** next to the filter; a new filter opens the groups that hold matches (the others are hidden), and they fold again by hand (before, a filter held every group open); each group (ECU, APID / CTID, message) has a checkbox for all its shown arguments (ticked: all are signals, a dash: some), so a whole group is added or removed at once (removed: their lanes go too), and a 📈 that plots all of them (picking them; again: none plotted, still picked); a FIBEX signal in the panel's list has a **−** that unpicks it (its lane goes too). **Panel layout (owner, 2026-10-28: many signals left no room for the browser; the list was cut at the right):** with FIBEX files loaded, the signal list and the FIBEX browser are two parts with a divider to drag, each scrolling on its own; the New signal form is folded under the list (an edit opens it); the panel's help is an ℹ hover; the panel starts 500 points wide; a value gets the room the other columns leave (owner, 2026-10-28: widen the panel to see more; long values cut with …, the hover has all of it), and a time — `@time` and every signal of kind time — is shown as long as fits: date and time to the µs, to the ms, then the time of day to the µs, the ms, the second (the full time in the hover); names keep their end, so a row's ✎ / − are in view. Tick an argument to make it a signal of the tab, or 📈 to plot it (which ticks it); it is then a signal like the others (`@free_slots < 10`, events and states, kind and scope), tagged FIBEX. Its value is the argument itself (`SignalDef::argument`: the messages `mid == N AND ecu == "E"` match, `LogSource::argument` decodes argument *n* of each), no regex. Names come from the argument's `ho:SHORT-NAME` (owner, 2026-10-25: prefer short names) — its SIGNAL's, else its PDU's when the PDU holds only it — unless that name only says a type (`S_UINT16`, `S_U16`, `INT32`), looks generated (`PDU_11_1`, `ID_12`, `P10_0`) or the signal is shared by several PDUs; `coolantTemp` → `coolant_temp`, shown as `"coolantTemp"`. Else from the last phrase before the argument (`Queue almost full. Free slots:` → `free_slots`), else the label of the argument before it in the message, else `m<id>_<n>`; made unique with the message id and argument place, and the ECU when two ECUs describe the same id (`Fibex::arguments`). `nerka-gui --plot NAME` picks a FIBEX argument of that name at startup. Forgetting the FIBEX files drops the picks.

## Protocol definitions (built: core, CLI, GUI)

Owner, 2026-11-08: protocols in captures described in a file, **declarative**, in an open standard where one fits: a **Kaitai Struct** (`.ksy`) structure plus Nerka's `-nerka:` section, `-nerka-text` templates and `-nerka-partial` (keys Kaitai ignores); compiled at load time; native readers stay; DLT as a definition is the stress test, compared with native DLT and benchmarked against it (speed best effort); the comparison is not a feature of the released core. Payload text by **templates** (owner chose them over native hooks). **Matching rules for every protocol**: a port alone, or source / destination address, ports, VLAN; a definition carries default rules, the user's replace them. **GUI (owner, 2026-11-08):** Settings holds the defaults; a tab's **Files…** window chooses each capture's protocols at any time (a question on File → Open was tried and dropped: "constant access via Files…"); the rules editor shows a field per condition (a text field of rules wasn't clear enough). Design, language subset, sections: **`protocol-definitions.md`**.

- **Core** (`core/src/input/proto/ksy/`, no dependency): YAML-subset reader, Kaitai's expression language, templates, a static tree of nodes with every name bound; header positions, `if`s and small instances memoized in 256-entry tables keyed by one message byte (`htyp` for DLT); types inside lists compiled into straight decoders (`plan.rs`), an element decoded once into a record; per-message state in a scratch area reused on each thread (no allocation per message). Rules: `input/capture/route.rs` (`Match`, `Route`); the transport hands the router addresses, ports and VLAN tags; `CaptureOptions::{protocols, routes, disabled}`, `OpenOptions::disabled_for` (per capture).
- **CLI:** `--protocol FILE`, `--route NAME:RULE`, `--protocol-port NAME=PORT`, `--disable-protocol NAME` (all repeatable).
- **GUI:** Settings → Captures: protocols (on / off, **Rules ▸** table, Add definition… into `<config>/nerka/protocols`, ✖, Reload; prefs `route=` lines and `disabled_protocols`); a tab's Files… window: a toggle per protocol on each capture, Apply reads the files again.
- **Checked:** `core/tests/ksy_dlt.rs` with `examples/protocols/dlt.ksy` (name `DLTK`, payloads included): the same splits, fields, payload text, lines and detailed payload as native DLT for random, damaged and every-`htyp` messages; two-port and shared-port captures (rules by address and VLAN). Found: native DLT writes an id's control characters into its columns as they are (damaged messages only); not changed.
- **Benchmark** (1 GiB, 12.5 M messages, release, Windows, separate runs on the same pcap): same matches everywhere; header filters 1.9–4.2× native (`apid == NAV AND level >= WARN` 29 / 89 ms); payload regex 250 ms / 2.28 s, full-text search 285 ms / 3.19 s (~10×); opening 340 ms / 4.1 s (12×). On a 1.7 MB capture the full-text search went 730 → 77 ms over this work (native 7 ms). Open: splitting went from 242 to 302 ns per message while payload decoding came in.
