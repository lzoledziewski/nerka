# The owner's GUI decisions

The GUI as the owner decided it, feature by feature (moved from `status.md` on 2026-11-10, word for word). These are deliberate choices: keep them, and record a new decision here with its date when the owner makes one. The state of the project is in `status.md`, built features in `features.md`. Where the moved text says "above", "below" or "this file", it means the old `status.md`: its sections are now `status.md` (state, pending decisions, limitations, licensing), `gui-decisions.md`, `features.md` and `history.md`.

## GUI as of now (`ui/`)

Owner feedback is driving this; these are deliberate choices, keep them:

- **Filter and Search (owner, 2026-10-18):** the **Filter** decides what the **main view** shows (only the kept lines; every line without a filter). The **Search** looks only among those lines; its hits are listed in the **bottom pane** (clicking one moves the main view there) and coloured per query in both views; n / N jump between hits. This replaces the klogg layout (whole file on top, filter result below). Going to a line that the filter hides lands on the next kept line. The filter's matches are no longer tinted: every row in the main view matches it. The **Filter bar sits at the top**, under the tab bar and across the whole window; the Search box and its hits pane are at the bottom.
- **Line colours (owner, 2026-10-18):** each included library filter query can colour the whole lines it keeps in the main view. Off by default; switched on per query by clicking its swatch in the selection or its chip under the Filter box (filled = on). Where a line matches several, the later query in the selection wins. The cursor and selection are drawn over the colour. Without a filter (only signal queries picked, or the box cleared) the colours go on every line they match (issue #8, 2026-10-28). The search hits pane shows them too (owner, 2026-10-19). Colours follow the **selection**, not the Filter box text (owner, 2026-10-19): editing the box by hand keeps them (each lit node is searched among the lines the current filter keeps); removing a node from the selection removes its colour. No library-level default: a pack colour only picks the colour, it never switches highlighting on (owner: many packs must not cost conflicts or time). **One colour per query (owner, 2026-10-22):** a query's own colour, else a palette entry picked when it joins the selection (the first one no other query uses) and kept: the swatch, the chip, the line colour and its search hits all show it, and reordering, removing or switching other queries doesn't change it (before, the swatch was always blue while the chip and lines took a colour by position). A preset gets its entries again in order when used.
- **Presets (owner, 2026-10-19):** a bar above the Selection pane (**Preset** list + ⋮: New from this tab… → Keep (session only, `•`) or Save; Update '<name>' from this tab (overwrites the file of a saved one); Save to disk; Delete). A preset holds the selection in order (role, line colour, without-parents), copies of edited and new queries (an internal `_preset` pack), parameter values, and the boxes' typed text (the Filter box as "the selection" when it holds its expansion). Not stored: search history, the Search box's library picks. Using one replaces the tab's selection and runs both boxes. **Library edits follow (issue #7, 2026-10-28):** renaming a library query renames it in every preset that picks it (copies made from it and queries refining it too); deleting one removes its nodes from the presets (an edited copy of it stays, as a query of its own); saved presets are written again and the status line names them (`Preset::rename_query` / `remove_query`). Files: `%APPDATA%\nerka\presets\<name>.nerka-preset` (format and parser: `core/src/preset.rs`); a library query that isn't loaded any more is reported, not dropped.
- **Windows as sessions (owner, 2026-10-20):** `nerka-gui FILE…` hands its files to the nerka window **focused last** (it opens them as tabs and comes to the front) and exits; with `--new-window`, other startup options, or no files, a new window starts. Each window listens on a loopback port registered with a random token in `<config>/nerka/instances/<pid>` (rewritten on focus; stale entries are dropped), std only (`ui/src/instance.rs`). A tab's menu has **Move to window ▸** (owner, 2026-11-12: replaces Move to new window; the cheaper step before dragging tabs between windows): **New window**, then the other windows, each by its label (`<pid>.label` next to its registration: the window's name, its active tab, `+N tabs`); the tab's filter, search and selection go along as a temporary preset (a new window: `--preset-file`; another window: a `preset` line in the hand-off request, the file read and removed there). A window that is gone is said and dropped from the list; a window that has the files open already takes the state into that tab. **Settings** (⚙ or Ctrl+,; a window, not a menu: a menu closes on any click, so its fields couldn't be typed in) → **Name** names the window: the title becomes `<name> · <file> — nerka`, so Alt+Tab tells sessions apart (`--name` at startup).
- **Several files as one view (owner, 2026-10-20):** files opened together (Open dialog multi-select, dropping several, `nerka-gui a.dlt b.dlt`, a hand-off) become **one tab, one after another** in the order given, if they are of **one kind** (same columns and fields: plain text with plain text; DLT with DLT, captures included). **Messages of different protocols share one view (owner, 2026-11-08: "take DLT from one input and my custom proto from another pcap"):** a DLT file, or a capture whose protocols differ (another protocol found, one turned off in the Files window), joins the others in the mixed layout of a capture holding several protocols (`time`, `proto`, `info`, `payload`, every part's fields; `Concat::is_mixed`); plain text and JSON still open as separate tabs, saying why. Two 256 MiB DLT files as one view, before / after: `apid == NAV AND level >= WARN` 16.5–16.9 / 16.2–16.5 ms, `ecu == ECU1` 24.7–24.8 / 24.1–24.2 ms. Core: `input::concat::Concat` (`nerka_core::open_many`) adds a `file` field (`file == b.dlt`); the engine searches part by part (`LogSource::parts`), so each file keeps its fast path (single-file numbers unchanged: text `search ERROR` ~31 ms, DLT `apid == NAV AND level >= WARN` ~29 ms per GiB). Bookmarks stay in each file's own sidecar (`Bookmarks::load_for_parts` / `save_for_parts`). The tab is titled `a.dlt + 2` (hover lists the files); its menu can open the files as separate tabs. **Merging by time is not done**: what "time" means across files has to be defined first (owner).
- **A tab's files (owner, 2026-10-28):** the tab's menu → **Files…** opens a window listing the view's files in order: ↑ / ↓ move one, − removes it (a tab keeps one), **+ Add files…**, **Apply** reads them again as one view (`Tab::set_files`), keeping filter, search, selection and signals; the view stays on the same line of the same file if it is still there. The files shown stay until the new set is read, and stay if it can't be one view (different kinds: "Files not changed: …"). Sorting the files by time comes later (with merging by time).
- **Tabs**, one per open file (klogg-style). Each tab has its own filter, view positions and bookmarks. Opening an already-open file switches to its tab. Ctrl+Tab / Ctrl+Shift+Tab (or Ctrl+PgDn/PgUp) switch tabs; Ctrl+W, ✖, middle-click or the context menu close them.
- **Filter box:** a mode list (owner, 2026-10-19; `search-modes.md`): **Auto** (default: plain words are an exact phrase, NFD syntax a query, they mix, and a box that isn't a valid query is literal text; Ignore case and Invert), **Text** (literal by default; a **Regex** checkbox switches to regex; also Ignore case and Invert) and **NFD** (strict; on an error, **Search as text instead**). A preview line under the box says how it will be read (`→ text: …` / `→ query: …`). Library picks put the box into NFD mode; the library is not affected by Auto. Its button is **Filter** (it was labelled Search, which was confusing). **Clear** next to it (issue #16, 2026-10-22), as in the Search box: enabled while a filter is applied, it empties the box so the main view shows every line again (↑ in the box brings the filter back). The row is laid out right to left so it never gets wider than the window. If it did, the result view's scrollbar would end up off-screen (that was a real bug).
- **When a search runs (owner's decision):** only on Enter or the Search button. Ticking Regex / Ignore case / Invert, switching the mode or picking a history entry only changes the box's settings or contents; nothing runs until Enter. The last mode + checkbox combination is saved to `%APPDATA%\nerka\prefs` (or `$XDG_CONFIG_HOME/nerka/prefs`) and becomes the default for new tabs. Only a mode **picked in the box's list** is saved (owner, 2026-11-06): a mode set for the box (the selection's NFD, 🔍 Search, a history entry, *Search as text instead*) doesn't change the default.
- **Search history:** the 🕘 button lists recent filters; picking one fills the box. They are stored in `%APPDATA%\nerka\history` (or `$XDG_CONFIG_HOME/nerka/history`) as `text|regex|query<TAB>pattern`, using `core::SearchHistory`.
- **Search box history (owner, issue #5):** the Search box has its own history, kept apart from the filters in `search-history` next to `history` (same format), with its own 🕘 button. Searches from the box (Enter / Find) and from a library 🔍 are recorded. In both boxes ↑ / ↓ step through the history shell-style (↓ past the newest entry gives back what was typed; typing stops browsing); like the 🕘 menu, this only fills the box, nothing runs until Enter.
- **Arrow keys (owner, 2026-10-26: they went through buttons):** a focused log view keeps ↑ / ↓ / ← / → and Esc (egui moved the focus to the nearest widget); the main view takes ↑ / ↓ / Page Up / Page Down whenever no text box or other log view has the focus (after a click on a button, before any click).
- **Text selection:** drag, Shift+click, double-click (word), Shift+arrows (lines), Ctrl+A, Esc. Ctrl+C copies the selection, or the current line if nothing is selected (at most 100k lines). The right-click menu has Copy, Select all, Show whole line and Toggle bookmark. **Picked lines** (issue #12, 2026-10-20): Ctrl+click (or Ctrl+Space on the cursor line) picks or unpicks single lines anywhere, marked across the full width; Ctrl+C or the menu copies the picked lines whole in file order; a plain click or Esc clears them; picks are file lines, so they stay when the filter changes.
- **Long lines (owner, issue #6):** a horizontal scrollbar appears under a view when the visible lines are wider than it (Shift+wheel and ← / → still scroll too). **Enter** (or the right-click menu's **Show whole line…**) opens a line window: for a table (DLT) the header columns as a name / value grid, then the message with its own line breaks and tabs as the logger wrote them (`LogSource::line_detail` in core; the table row shows them as spaces), wrapped or not, selectable, with **Copy message** and **Copy line** (columns tab-separated, the message's line breaks kept); plain text shows the whole line (not cut at 4 KiB) with **Copy**. The window shows at most 1 MiB; Copy copies everything.
- **Go to line:** Ctrl+G / Ctrl+L opens a dialog. There is no toolbar field (the owner asked for it to be removed).
- **Look:** no tint on matching lines in the main view (the owner disliked the blue); the cursor line is neutral grey. Scrollbar thumbs use the text colour at 50% and are 14 px wide.
- **Scrolling:** the views read raw mouse-wheel events (3 rows per notch), not egui's smoothed delta; the smoothing made text look smeared. Rows and text origins snap to physical pixels. A headless test (`view::tests::wheel_scrolls_hovered_view_by_whole_lines`) runs the app's panel layout and injects wheel events. Use that pattern for other GUI input tests.
- **Icon:** a kidney ("nerka") with messy log lines going in and clean lines coming out, drawn in code (`ui/src/icon_art.rs`, no image file). It shows on the window and taskbar, and since 2026-10-20 (owner) also as the **`.exe` file icon**: `ui/build.rs` renders the same drawing at 16–256 px into an `.ico` and embeds it with `winresource` (build dependency, Windows only, MIT, one small dependency of its own; also writes the version info from `Cargo.toml`). The resource compiler comes with the Windows SDK; without it the build warns and goes on without the file icon.
- **About:** an "ℹ About" button at the right of the toolbar (or F1) opens a modal with the icon, version, author (© 2026 Łukasz Żołędziewski, email as a mailto link), licence and repository link. All of these come from `Cargo.toml` (`env!`), so keep `authors` / `repository` `.workspace = true` in each crate.
- **Search manager (POC):** 📚 (Ctrl+Shift+L) opens two panes: the **Library** (a tree: refining queries under their parent; `+` or drag adds to the selection, `🔍` searches, `⋮` edit / refine / exclude, `+ New query`) and the **Selection** (ordered filter queries; drag to reorder, `+` / `−` role, `✎` edit, save to a pack; owner, 2026-10-18: no checkboxes). **Apply** puts the selection into the Filter bar. Searching is an action: `🔍` → **Search for it** (replace) or **Add to search (OR)** (typed text becomes a query first). The Search box looks only inside the filter result and colours hits per query (n / N jump between search hits). Query names may contain spaces (quoted in pack files).
- **Bookmarks:** these work (`m`, `b` / `B`, notes in the side panel, `<log>.nerka-marks` sidecar; the panel shows each line wrapped to two rows, ▸ / ▾ or a click unfolds the whole line), but the owner wasn't sure about them yet. Hovering the 🔖 button explains them. Ask before investing more in them. **Names (owner, 2026-10-25: the line number as id is off):** each bookmark has a short name, `B1`, `B2`… (the first free one when it is made), shown and renamed in the panel (the field next to its line link; set when the field loses focus, emptied: a free name again); the plot and the CLI's `marks` show it. The sidecar line is `<line>\t<note>\t<name>`; an older two-column sidecar gets names in line order when read.

- **Bookmarks in filters and searches (owner, 2026-11-01, designed from a mockup, built for 0.1.0-alpha.9):** NFD has a regular field **`bookmark`** (`dsl/mod.rs`, `Cond::Bookmark`): alone it holds on a bookmarked line (`level >= ERROR OR bookmark` keeps the marked lines in a filter); `==` / `!=` compare the bookmark's name, `~` / `!~` match its name or its note (`bookmark ~ /fan/`); a line without one only satisfies `!=` and `!~`. Queries get the tab's bookmarks with `Query::with_bookmarks` (`Filter::with_bookmarks`); without them no line has one. In Auto, `bookmark` alone is text, next to other NFD it is the field. The GUI gives them to the filter, the search and the line colours, and runs whatever uses `bookmark` again when a bookmark is added, removed, renamed or gets a note (the filter that ran, not the box's text if it was edited since). The CLI reads the log's `.nerka-marks`.
- **Notes in the views (owner, 2026-11-01):** Bookmarks panel → *Notes in the views*, one setting for all tabs (`prefs`: `bookmark_notes`): **Line before** (default, the owner's choice: the note on a row of its own above its line, `🔖 name · note`, never scrolled sideways), **End of line** (dimmed after the text), **Column** (a last `🔖 note` column in tables; the column before it gets a width of 60 if it had none; plain text logs show the note on the line before) and **Off**. Only bookmarks with a note show one. Copying takes the notes along as the view shows them, as `// name · note` without the line's other fields (owner, 2026-11-01): a line before the line (Line before; Column on plain text), or after its text (End of line: two spaces; Column: one more cell); a partial line gets it only at the end it covers. A note row isn't a log line: no number, not copied by itself, ↑ / ↓ skip it, and a click on it selects its line (`view.rs`: the rows are laid out in slots; `fits` counts the lines a page holds).
- **Tweaks for 0.1.0-alpha.9 (owner, 2026-11-01):** **📈 Plot** in the top bar (next to 📷) shows or hides the active tab's plot, as the button in the Signals panel does. **Hovering a bookmarked line** in a view shows the bookmark's name and note at the pointer (`view.rs`). **Search chips** (the Search box's library queries): ✖ shows while one is hovered, and a click removes that query from the box (the others are searched again; the last one clears the search; `Tab::remove_search_term`). Filter chips keep their click (line colour).
- **From the owner's use (2026-11-09, review U1, U5):** the plot labels **every plotted lifecycle**: a row of labels and a dash of its own each (up to 4 rows; more share the last), and the hover over a start line names every lifecycle starting there (before, ECUs booting together showed only the first one's labels). A kept plot changes only on Keep changes / Save (Signals → Plot above). Checks per tab (U2, owner, 2026-11-10): on / off and Auto / ▶ Run are each tab's, a check's saved flag is what new tabs start with, the last Auto choice is new tabs' (`checks.md` → Per tab). U4 cancelled (owner, 2026-11-10): a `per` check's overall result keeps judging the whole log, reboots included, and counting (`checks.md`). **Windows and one configuration (U3, owner, 2026-11-10):** each window is still a process of its own. When it gets the focus back and packs, presets, plots, checks or signals changed meanwhile, a **notice bar** says what ("Changed in another window: check storm added, plot drive") with **Reload** and **Not now**; nothing is read by itself, so a debugging session isn't changed under the user (owner, 2026-11-10: notice only, not a modal; prefs don't raise it). ⚙ Settings → **Reload configuration** reads everything again, prefs too; session items (`--check`, `--signal`, `•` presets and plots) and each tab's own state stay, open tabs keep how their files were read. A save of checks, signals or prefs writes this window's changes into what is in the file now (a merge by name, or by key for prefs; both changed: this window's kept, said in the status), so another window's change isn't lost (`ui/src/sync.rs`). Still whole-file, last writer wins: the filter and search histories and the library's use counts; one plot, preset or pack saved from two windows. Still open from that list: query signals with saved signals' options (U6), pulling a needed query into the selection (U7): `docs/dev/review/2026-11-09-findings.md` → Open findings carried forward.
- **Open errors and the command line (review 2026-11-09, R7):** files that can't be opened are named, with the whole reason, in a **Cannot open** window (OK / Esc) as well as the status line; with several files, the one that failed. `nerka-gui --help` / `--version` print to the terminal (a release build on Windows attaches to its parent's console) and an unknown option is an error (exit 2), not a file; `--` ends the options. A running window takes the files only when nothing but files is given.
- **Screenshots to the clipboard (owner, 2026-10-25):** 📷 in the top bar (or Ctrl+Shift+S) copies an image of the window; 📷 in the plot's header copies the plot alone (in its own window too). egui reads the frame's pixels and eframe puts the image on the clipboard (`ui/src/shot.rs`); no new dependency.

- **Theme, Reload, sorting one file (owner, 2026-11-12, from use on Linux):** ⚙ Settings → **Theme**: System (default), Light, Dark, saved in `prefs` (`theme`). A tab's menu → **Reload** reads its files again from disk, as a change of times does (filter, search, selection and line stay). A tab of one file that knows its times (DLT, captures) has **Sort by time** where several files have Merge by time: a stable sort of all its lines by time (a line without a time goes with the one before it), so lines whose times go back move; Merge by time still keeps each file's own order. Sorting one file is not the remembered Merge by time choice: new one-file tabs open unsorted.

## Checking the GUI visually

`tools/screenshot.ps1` launches the debug build, captures its window to a PNG and closes it again. Read the PNG to check layout and rendering. This is how the off-screen scrollbar was found. `-Keys` sends keystrokes before the capture (SendKeys syntax), e.g. `-Keys '{F1}'` for the About dialog. Don't close or kill nerka-gui windows the owner has open; if the exe is locked by one of them, build with `--target-dir target/<name>` and pass `-Exe`.
