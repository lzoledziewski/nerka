## GUI as of now (`ui/`)

Owner feedback is driving this; these are deliberate choices, keep them:

- **Filter and Search (owner, 2026-10-18):** the **Filter** decides what the **main view** shows (only the kept lines; every line without a filter). The **Search** looks only among those lines; its hits are listed in the **bottom pane** (clicking one moves the main view there) and coloured per query in both views; n / N jump between hits. This replaces the klogg layout (whole file on top, filter result below). Going to a line that the filter hides lands on the next kept line. The filter's matches are no longer tinted: every row in the main view matches it. The **Filter bar sits at the top**, under the tab bar and across the whole window; the Search box and its hits pane are at the bottom.
- **Line colours (owner, 2026-10-18):** each included library filter query can colour the whole lines it keeps in the main view. Off by default; switched on per query by clicking its swatch in the selection or its chip under the Filter box (filled = on). Where a line matches several, the later query in the selection wins. The cursor and selection are drawn over the colour. Without a filter (only signal queries picked, or the box cleared) the colours go on every line they match (issue #8, 2026-10-28). The search hits pane shows them too (owner, 2026-10-19). Colours follow the **selection**, not the Filter box text (owner, 2026-10-19): editing the box by hand keeps them (each lit node is searched among the lines the current filter keeps); removing a node from the selection removes its colour. No library-level default: a pack colour only picks the colour, it never switches highlighting on (owner: many packs must not cost conflicts or time). **One colour per query (owner, 2026-10-22):** a query's own colour, else a palette entry picked when it joins the selection (the first one no other query uses) and kept: the swatch, the chip, the line colour and its search hits all show it, and reordering, removing or switching other queries doesn't change it (before, the swatch was always blue while the chip and lines took a colour by position). A preset gets its entries again in order when used.
- **Presets (owner, 2026-10-19):** a bar above the Selection pane (**Preset** list + ⋮: New from this tab… → Keep (session only, `•`) or Save; Update '<name>' from this tab (overwrites the file of a saved one); Save to disk; Delete). A preset holds the selection in order (role, line colour, without-parents), copies of edited and new queries (an internal `_preset` pack), parameter values, and the boxes' typed text (the Filter box as "the selection" when it holds its expansion). Not stored: search history, the Search box's library picks. Using one replaces the tab's selection and runs both boxes. **Library edits follow (issue #7, 2026-10-28):** renaming a library query renames it in every preset that picks it (copies made from it and queries refining it too); deleting one removes its nodes from the presets (an edited copy of it stays, as a query of its own); saved presets are written again and the status line names them (`Preset::rename_query` / `remove_query`). Files: `%APPDATA%\nerka\presets\<name>.nerka-preset` (format and parser: `core/src/preset.rs`); a library query that isn't loaded any more is reported, not dropped.
- **Windows as sessions (owner, 2026-10-20):** `nerka-gui FILE…` hands its files to the nerka window **focused last** (it opens them as tabs and comes to the front) and exits; with `--new-window`, other startup options, or no files, a new window starts. Each window listens on a loopback port registered with a random token in `<config>/nerka/instances/<pid>` (rewritten on focus; stale entries are dropped), std only (`ui/src/instance.rs`). A tab's menu has **Move to new window** (its filter, search and selection go along as a temporary preset). **Settings** (⚙ or Ctrl+,; a window, not a menu: a menu closes on any click, so its fields couldn't be typed in) → **Name** names the window: the title becomes `<name> · <file> — nerka`, so Alt+Tab tells sessions apart (`--name` at startup).
- **Several files as one view (owner, 2026-10-20):** files opened together (Open dialog multi-select, dropping several, `nerka-gui a.dlt b.dlt`, a hand-off) become **one tab, one after another** in the order given, if they are of **one kind** (same columns and fields: plain text with plain text; DLT with DLT, captures included); mixed kinds open as separate tabs, saying why. Core: `input::concat::Concat` (`nerka_core::open_many`) adds a `file` field (`file == b.dlt`); the engine searches part by part (`LogSource::parts`), so each file keeps its fast path (single-file numbers unchanged: text `search ERROR` ~31 ms, DLT `apid == NAV AND level >= WARN` ~29 ms per GiB). Bookmarks stay in each file's own sidecar (`Bookmarks::load_for_parts` / `save_for_parts`). The tab is titled `a.dlt + 2` (hover lists the files); its menu can open the files as separate tabs. **Merging by time is not done**: what "time" means across files has to be defined first (owner).
- **A tab's files (owner, 2026-10-28):** the tab's menu → **Files…** opens a window listing the view's files in order: ↑ / ↓ move one, − removes it (a tab keeps one), **+ Add files…**, **Apply** reads them again as one view (`Tab::set_files`), keeping filter, search, selection and signals; the view stays on the same line of the same file if it is still there. The files shown stay until the new set is read, and stay if it can't be one view (different kinds: "Files not changed: …"). Sorting the files by time comes later (with merging by time).
- **Tabs**, one per open file (klogg-style). Each tab has its own filter, view positions and bookmarks. Opening an already-open file switches to its tab. Ctrl+Tab / Ctrl+Shift+Tab (or Ctrl+PgDn/PgUp) switch tabs; Ctrl+W, ✖, middle-click or the context menu close them.
- **Filter box:** a mode list (owner, 2026-10-19; `search-modes.md`): **Auto** (default: plain words are an exact phrase, NFD syntax a query, they mix, and a box that isn't a valid query is literal text; Ignore case and Invert), **Text** (literal by default; a **Regex** checkbox switches to regex; also Ignore case and Invert) and **NFD** (strict; on an error, **Search as text instead**). A preview line under the box says how it will be read (`→ text: …` / `→ query: …`). Library picks put the box into NFD mode; the library is not affected by Auto. Its button is **Filter** (it was labelled Search, which was confusing). **Clear** next to it (issue #16, 2026-10-22), as in the Search box: enabled while a filter is applied, it empties the box so the main view shows every line again (↑ in the box brings the filter back). The row is laid out right to left so it never gets wider than the window. If it did, the result view's scrollbar would end up off-screen (that was a real bug).
- **When a search runs (owner's decision):** only on Enter or the Search button. Ticking Regex / Ignore case / Invert, switching the mode or picking a history entry only changes the box's settings or contents; nothing runs until Enter. The last mode + checkbox combination is saved to `%APPDATA%\nerka\prefs` (or `$XDG_CONFIG_HOME/nerka/prefs`) and becomes the default for new tabs.
- **Search history:** the 🕘 button lists recent filters; picking one fills the box. They are stored in `%APPDATA%\nerka\history` (or `$XDG_CONFIG_HOME/nerka/history`) as `text|regex|query<TAB>pattern`, using `core::SearchHistory`.
- **Search box history (owner, issue #5):** the Search box has its own history, kept apart from the filters in `search-history` next to `history` (same format), with its own 🕘 button. Searches from the box (Enter / Find) and from a library 🔍 are recorded. In both boxes ↑ / ↓ step through the history shell-style (↓ past the newest entry gives back what was typed; typing stops browsing); like the 🕘 menu, this only fills the box, nothing runs until Enter.
- **Arrow keys (owner, 2026-10-26: they went through buttons):** a focused log view keeps ↑ / ↓ / ← / → and Esc (egui moved the focus to the nearest widget); the main view takes ↑ / ↓ / Page Up / Page Down whenever no text box or other log view has the focus (after a click on a button, before any click).
- **Text selection:** drag, Shift+click, double-click (word), Shift+arrows (lines), Ctrl+A, Esc. Ctrl+C copies the selection, or the current line if nothing is selected (at most 100k lines). The right-click menu has Copy, Select all, Show whole line and Toggle bookmark. **Picked lines** (issue #12, 2026-10-20): Ctrl+click (or Ctrl+Space on the cursor line) picks or unpicks single lines anywhere, marked across the full width; Ctrl+C or the menu copies the picked lines whole in file order; a plain click or Esc clears them; picks are file lines, so they stay when the filter changes.
- **Long lines (owner, issue #6):** a horizontal scrollbar appears under a view when the visible lines are wider than it (Shift+wheel and ← / → still scroll too). **Enter** (or the right-click menu's **Show whole line…**) opens a line window: for a table (DLT) the header columns as a name / value grid, then the message with its own line breaks and tabs as the logger wrote them (`LogSource::line_detail` in core; the table row shows them as spaces), wrapped or not, selectable, with **Copy message** and **Copy line** (columns tab-separated, the message's line breaks kept); plain text shows the whole line (not cut at 4 KiB) with **Copy**. The window shows at most 1 MiB; Copy copies everything.
- **Go to line:** Ctrl+G / Ctrl+L opens a dialog. There is no toolbar field (the owner asked for it to be removed).
- **Look:** no tint on matching lines in the main view (the owner disliked the blue); the cursor line is neutral grey. Scrollbar thumbs use the text colour at 50% and are 14 px wide.
- **Scrolling:** the views read raw mouse-wheel events (3 rows per notch), not egui's smoothed delta; the smoothing made text look smeared. Rows and text origins snap to physical pixels. A headless test (`view::tests::wheel_scrolls_hovered_view_by_whole_lines`) runs the app's panel layout and injects wheel events. Use that pattern for other GUI input tests.
- **Icon:** a kidney ("nerka") with messy log lines going in and clean lines coming out, drawn in code (`ui/src/icon_art.rs`, no image file). It shows on the window and taskbar, and since 2026-10-20 (owner) also as the **`.exe` file icon**: `ui/build.rs` renders the same drawing at 16–256 px into an `.ico` and embeds it with `winresource` (build dependency, Windows only, MIT, one small dependency of its own; also writes the version info from `Cargo.toml`). The resource compiler comes with the Windows SDK; without it the build warns and goes on without the file icon.
- **About:** an "ℹ About" button at the right of the toolbar (or F1) opens a modal with the icon, version, author (© 2026 Łukasz Żołędziewski, email as a mailto link), licence and repository link. All of these come from `Cargo.toml` (`env!`), so keep `authors` / `repository` `.workspace = true` in each crate.
- **Search manager (POC):** 📚 (Ctrl+Shift+L) opens two panes: the **Library** (a tree: refining queries under their parent; `+` or drag adds to the selection, `🔍` searches, `⋮` edit / refine / exclude, `+ New query`) and the **Selection** (ordered filter queries; drag to reorder, `+` / `−` role, `✎` edit, save to a pack; owner, 2026-10-18: no checkboxes). **Apply** puts the selection into the Filter bar. Searching is an action: `🔍` → **Search for it** (replace) or **Add to search (OR)** (typed text becomes a query first). The Search box looks only inside the filter result and colours hits per query (n / N jump between search hits). Query names may contain spaces (quoted in pack files).
- **Bookmarks:** these work (`m`, `b` / `B`, notes in the side panel, `<log>.nerka-marks` sidecar; the panel shows each line wrapped to two rows, ▸ / ▾ or a click unfolds the whole line), but the owner wasn't sure about them yet. Hovering the 🔖 button explains them. Ask before investing more in them. **Names (owner, 2026-10-25: the line number as id is off):** each bookmark has a short name, `B1`, `B2`… (the first free one when it is made), shown and renamed in the panel (the field next to its line link; set when the field loses focus, emptied: a free name again); the plot and the CLI's `marks` show it. The sidecar line is `<line>\t<note>\t<name>`; an older two-column sidecar gets names in line order when read.

- **Bookmarks in filters and searches (owner, 2026-11-01, designed from a mockup, built for 0.1.0-alpha.9):** NFD has a regular field **`bookmark`** (`dsl/mod.rs`, `Cond::Bookmark`): alone it holds on a bookmarked line (`level >= ERROR OR bookmark` keeps the marked lines in a filter); `==` / `!=` compare the bookmark's name, `~` / `!~` match its name or its note (`bookmark ~ /fan/`); a line without one only satisfies `!=` and `!~`. Queries get the tab's bookmarks with `Query::with_bookmarks` (`Filter::with_bookmarks`); without them no line has one. In Auto, `bookmark` alone is text, next to other NFD it is the field. The GUI gives them to the filter, the search and the line colours, and runs whatever uses `bookmark` again when a bookmark is added, removed, renamed or gets a note (the filter that ran, not the box's text if it was edited since). The CLI reads the log's `.nerka-marks`.
- **Notes in the views (owner, 2026-11-01):** Bookmarks panel → *Notes in the views*, one setting for all tabs (`prefs`: `bookmark_notes`): **Line before** (default, the owner's choice: the note on a row of its own above its line, `🔖 name · note`, never scrolled sideways), **End of line** (dimmed after the text), **Column** (a last `🔖 note` column in tables; the column before it gets a width of 60 if it had none; plain text logs show the note on the line before) and **Off**. Only bookmarks with a note show one. Copying takes the notes along as the view shows them, as `// name · note` without the line's other fields (owner, 2026-11-01): a line before the line (Line before; Column on plain text), or after its text (End of line: two spaces; Column: one more cell); a partial line gets it only at the end it covers. A note row isn't a log line: no number, not copied by itself, ↑ / ↓ skip it, and a click on it selects its line (`view.rs`: the rows are laid out in slots; `fits` counts the lines a page holds).
- **Tweaks for 0.1.0-alpha.9 (owner, 2026-11-01):** **📈 Plot** in the top bar (next to 📷) shows or hides the active tab's plot, as the button in the Signals panel does. **Hovering a bookmarked line** in a view shows the bookmark's name and note at the pointer (`view.rs`). **Search chips** (the Search box's library queries): ✖ shows while one is hovered, and a click removes that query from the box (the others are searched again; the last one clears the search; `Tab::remove_search_term`). Filter chips keep their click (line colour).
- **Screenshots to the clipboard (owner, 2026-10-25):** 📷 in the top bar (or Ctrl+Shift+S) copies an image of the window; 📷 in the plot's header copies the plot alone (in its own window too). egui reads the frame's pixels and eframe puts the image on the clipboard (`ui/src/shot.rs`); no new dependency.

## Next steps

**0.1.0 (owner, 2026-11-01): the non-minor findings of a code review** (plugins, more protocols, multi-row records). Scope and order to settle with the owner:

- **Bookmarks anchored by content, not row number — built (2026-11-01, the owner took the recommendations).** A source gives each line an `Anchor` (`LogSource::anchor`: the byte offset the line starts at in its file, none if its bytes aren't contiguous there, e.g. a reassembled datagram or a syslog copy; and an FNV-1a hash of its first 64 bytes) and finds lines by offset in one pass (`lines_at`). The sidecar gets a 4th column `@<offset>:<hash>` (`@-:<hash>` without an offset); older sidecars load as they are (rows), and older nerka versions would show the column as part of the name (0.x: formats can change). Loading (`Bookmarks::resolve`) puts each bookmark on the line at its offset if the hash matches, else on the nearest line with that hash within 5,000 rows of its old one; one that isn't found **stays on its old row, unsure** (owner: not dropped, no "lost" list): `?` after its name in the Bookmarks panel (hover explains), the views' notes and hover, and the CLI's `marks`; it keeps the anchor it was saved with until its name or note is edited (then it is sure on that line). Content hash only, no file size or time (owner). A view of several files resolves each file against its own source.
- **A core session.** What runs again when the bookmarks, signals or filter change lives in `ui/src/main.rs` (5,300 lines; `Tab` 46 fields): move it into a core `Session` / view model with one `QueryContext` (schema, signals, bookmarks) instead of a `with_*` pass per feature, so the CLI and plugins share it.
- **Split `LogSource`.** About 20 methods, some format-specific (`argument` for FIBEX, the text fast path's `contiguous` / `line_start` / `line_of_offset`), fields fetched per line through the trait, field names `&'static str`. Proposed: a small rows trait plus optional capabilities; runtime field names; more field kinds (float, bool, time) for JSON.
- **Protocols as decoders — built (2026-11-01, owner: "DLT just another protocol", proved with real ones: SOME/IP and syslog both; one table with shared columns for mixed captures).** `core/src/input/proto/`: a `Protocol` trait (`split` a datagram into messages, `render` / `detail` the columns after `time`, `field`, `level`, `argument`; `delimited` says whether a message carries its own length) and one source for every container, `Records` (an index of `Framed` entries, 16 B: offset, side-buffer bit, 11-bit channel, 4-bit protocol, time; a `.dlt` file keeps its 8 B offsets and reads time and ECU from each storage header). `DltFile` is `Records` (type alias). The capture router maps UDP destination ports to protocols (`CaptureOptions`: `dlt_udp_ports` 3490, `someip_udp_ports` 30490, `syslog_udp_ports` 514; CLI `--someip-port`, `--syslog-port`; GUI ⚙ → Captures: UDP ports; a port listed twice goes to the first). One protocol in a source: its own columns and fields plus `proto`. Several: columns `time`, `proto`, `info` (the protocol's columns before its payload, in one cell), `payload`, and every protocol's fields (a field of the same name and kind is one field: `type`, `payload`); a message's missing fields only satisfy `!=` / `!~`. `proto` is a name field (`FieldKind::Name`): `==` / `!=` ignore case, so `proto == syslog`, `SYSLOG` and `Syslog` are the same (owner, 2026-11-01). **SOME/IP** (`proto/someip.rs`): headers only (service, method, client, session, iface, type, rc, len; payload as hex; `SD` marked; level Error for ERROR types or a return code other than E_OK, else Info); no TCP, no SOME/IP-TP reassembly, payloads not decoded (FIBEX / ARXML later). **Syslog** (`proto/syslog.rs`): RFC 5424 and RFC 3164 over UDP (facility, severity as the level, host, app, pid, msgid, the message's own stamp); not delimited, so the capture keeps each message behind its length in the side buffer. Still DLT-specific: MF4 `DLT_Frame` groups; FIBEX applies to the DLT protocol; `open_with` still sniffs by if / else (a registry when a container needs one).
- **Multi-row records — text records built (2026-11-01; the owner took the recommendations: one row per record first, taller rows later; the split auto-detected or chosen per tab and remembered per file; JSON Lines and pretty JSON with `a.b.c` keys and arrays as text; text records before JSON).** `core/src/input/records.rs`: `RecordFile`, a text file read as records by a `RecordSplit`: `start=/REGEX/` (a line matching it at its start begins a record; lines before the first are a record too), `blank` (blank lines separate records), `sep=/REGEX/` (matching lines separate them, in neither) or `lines`. One pass at open (16 B per record: start and end); a row's bytes are the record's, line breaks included, so a regex can span its lines and the buffer scan still works (the engine now verifies a hit that starts before its row: text between records belongs to none). The level is detected from the record's start. Views draw a record's line breaks as `⏎` (one character each, so selections keep their columns); copying and the line window keep the breaks. Bookmarks move between the line and record views of a file (`LogSource::line_holding`; anchors hash a line's or record's first line only, `Anchor::of_text`). CLI `--records SPEC`; GUI: a tab's menu → Records… (text tabs), remembered per file in `<config>/nerka/records`. **JSON records — built (2026-11-02):** `RecordSplit::Json` (`core/src/input/json.rs`, an own reader, no dependency): each top-level value is a record (JSON Lines, objects one after another; text that isn't a value is skipped to the next line), or each element if the file is one array (pretty JSON). Keys are fields: every key path with a value in the first 1,000 records, lower case, nested keys joined by `.` (`ctx.user`), typed by what they hold (whole numbers `U64`, other numbers `F64`, the rest text; arrays and objects as their text; a key holding numbers and text is text); `raw`, `level`, `bookmark` and names NFD can't write aren't fields. A `level` / `severity` / `lvl` / `loglevel` key is the row's level (names, or bunyan / pino numbers 10–60). Field names are owned now (`FieldDef::new` / `FieldDef::owned`), and NFD has a float kind (`FieldKind::F64`). **Automatic** by default: a file whose start is a JSON object (or an array of them; `[INFO] …` stays text) is read as JSON unless the tab or `--records` says otherwise; the Records window has Automatic and JSON, and remembering "lines" turns detection off for a file. Benchmark (256 MiB JSON Lines, 1.8 M records, release): open 0.22 s; `level >= ERROR` 16 ms, `status >= 500` 24 ms, `ctx.user == carol AND latency > 45` 21 ms, `msg ~ /timeout/` 20–32 ms, `search timeout` 8 ms. Not yet: a schema that grows with keys seen after the sample, concat of JSON files with other keys (refused as another kind). **Next:** rows taller than one line (folded / unfolded records in place).
- **Transform sources** (script output, awk-style records): materialised into a file and opened as text, with a row → original-row map so jumps and bookmarks go back to the source.

## DLT and captures (built)

DLT import was the focus from 2026-10-18 (owner); `.dlt` files, pcap / pcapng and MF4 are read now. The search manager came next and is built too (below). Design of the layers: `sources-and-signals.md`.

Decided for DLT: own zero-copy parser in `core/src/input/dlt/` (no crate, no dependency); synthetic test data only (a DLT writer + `gen_dlt` example); shown as a **table with aligned, resizable columns** in our own view (no column sorting; each row is still one tab-separated text line, so search, highlight and copy keep working).

Done (step 1): `LogSource::line_bytes` returns `Cow`; sources can supply a field schema, per-line field values and levels; `Event` is lazy over `(source, line)`, so header-only filters never render a line; the DSL accepts source fields (`apid == NAV`, `mcnt >= 0x10`), resolved by `Query::bind` / `compile_for`. Text-log benchmark unchanged (1 GiB: `search ERROR` ~30 ms, `level >= ERROR` ~31 ms).

Done (step 2): own DLT reader in `core/src/input/dlt/` (no new dependencies). `nerka_core::open` picks DLT or text by content (the GUI too, since step 3).
- Index = one `u64` offset per message (~8 B/msg). Headers are read in place, so header-only filters never decode payloads.
- Fields: `ecu apid ctid type mcnt tmsp seid mid mode payload`; `payload` is the decoded payload column only (unlike `raw`, which spans every column), e.g. `payload ~ "timeout"`, and is checked after the header conditions; `mode` is `verbose` / `non-verbose` (`mid` stays empty on verbose messages, since 0 is a valid message id); `level` comes from the header (`VERBOSE` is accepted as an alias for `TRACE`).
- Line = tab-separated columns `time tmsp ecu apid ctid type payload` (time is the storage time in **local time or UTC**, see "Times: local or UTC"; `type` is the level for log messages, e.g. `error`).
- Payload: verbose bool/int/float/string/raw/trace info, with VARI names and units; arrays, structs and fixed-point fall back to `<undecoded> hex`. Non-verbose: `[id] hex`. Control: service name, status, version string.
- Corrupt data: resync on the next `DLT\x01`, skipped bytes counted. Files without storage headers aren't supported.
- `writer` module + `examples/gen_dlt.rs` produce synthetic files.
- 1 GiB synthetic DLT (12.5M messages): index 280 ms (single-threaded), 95 MiB; `ecu == ECU1` 37 ms, `apid == NAV AND level >= WARN` 29 ms, `level >= ERROR` 32 ms, `raw ~ /timeout/` 288 ms (renders every line), `apid == NAV AND raw ~ /timeout/` 60 ms.

Done (step 3): the GUI opens files via `nerka_core::open`; sources with columns (`LogSource::columns`, DLT) are shown as a **table** in the existing view: a header row with the column names, cells aligned at column boundaries, faint dividers, and a divider drag in the header resizes the column (widths belong to the tab, shared by the main and filter views; not saved yet). Text that doesn't fit a cell is hidden and marked with "…". Selection, double-click, search highlighting and copy still work on the line text (copy keeps the tabs, so it pastes into a spreadsheet as columns). Plain text looks as before. The Open dialog lists `.dlt` files.

Done (step 4, 2026-10-20): **DLT in pcap / pcapng captures**, read in place (no temporary `.dlt`): `core/src/input/capture/` (container `pcap.rs`: pcap µs/ns both byte orders, pcapng sections / interfaces / `if_tsresol` / `if_tsoffset`; transport `net.rs`: Ethernet, stacked VLAN tags, Linux SLL / SLL2, raw IP, loopback, IPv4 / IPv6 with **fragment reassembly** in any order (30 s capture-time timeout, at most 4096 pending); router: UDP destination ports, default **3490** only (the DLT protocol's port; owner, 2026-10-20), configurable: CLI `--dlt-port` (repeatable), GUI ⚙ → UDP ports (saved in `prefs` as `dlt_ports`, used for captures opened afterwards), core `OpenOptions` / `CaptureOptions`). The DLT reader was generalised: a message takes its storage time and ECU from its index entry (`Framed`, 16 B: offset with a side-buffer bit and a 15-bit capture channel, time), so a `.dlt` file is the simplest case; reassembled datagrams live in a side buffer. A message gets the time of the frame that completed its datagram; its ECU is its own (WEID). `nerka_core::open` recognises captures by content; the GUI's Open dialog lists `.pcap` / `.pcapng`. No new dependency. Benchmark: `big.dlt` → `big.pcap` with `examples/dlt_to_pcap` (870 MB, 12.5 M messages, VLAN, several messages per datagram, every 400th datagram fragmented): index ~300 ms (`.dlt`: ~255 ms), the same match counts and search times as the `.dlt`; the `.dlt` numbers are unchanged by the refactor. **MF4** (2026-10-20, `capture/mf4.rs`, own reader, no dependency): block tree over the mapped file; unsorted (1/2/4/8-byte record ids) and sorted data; DT / DL / HL (records spanning data blocks are copied to the side buffer); VLSD channel groups (paired with their frame group by order) and SD blocks (by offset); **Compressed data** (DZ blocks, deflate, transposed or not; 2026-10-26, `capture/unpack.rs`, dependency `miniz_oxide`): unpacked once, as a stream, into a file in the **unpack cache** (`%LOCALAPPDATA%\nerka\cache`, `~/.cache/nerka`), which is mapped like any log — RAM doesn't grow with the number of tabs, and the reader stays zero-copy (owner, 2026-10-26: unpacking into memory would fill RAM with several tabs). The block tree is read from the original file, the records from the cache file (every data block, unpacked or copied, in the order the tree reaches them; `Layout` maps a block to its place). The cache file is named after the original's path, size and modification time, so opening the file again maps it without unpacking; written to a temporary name and renamed (two tabs or instances can open the same file). The cache keeps under a limit (default 8 GiB; GUI ⚙ → Compressed MF4: size limit, usage, Clear) by removing the least recently used files after writing one (an open one stays on Windows). CLI `--unpack-dir DIR`; without a cache folder (core's default, tests) the data is unpacked into memory. Not yet: keeping only the DLT bytes while unpacking (would make the cache smaller when the log has other traffic); `.gz` / `.zst` captures (same approach). Benchmark (1 GiB `big.dlt` → `examples/dlt_to_mf4`, 12.5 M messages, release, Windows): uncompressed MF4 index 1.35 s before, 1.33 s after, search ~29 ms either way; deflated in 4 MiB DZ blocks (264 MB): first open 2.9 s (unpacking), then 1.33 s from the cache; one DZ block for all records and one for all signal data: 2.9 s, then 0.85 s (a cold cache file read from disk: ~3 s); search ~29 ms in every case. Groups by channel names (`ETH_Frame.*` → Ethernet frames into the same transport and port router as pcap; `DLT_Frame.*` → DLT directly, its `ECU_ID` the fallback ECU), else by shape (an Ethernet bus-event group, as X2E loggers write). Time = header start + master channel through its linear conversion (none: the raw value in seconds, as the spec says). Not yet tried on real-world files (own or public). Layers: `sources-and-signals.md`.

### DLT decisions (owner, 2026-10-18)

- **Own parser, no crate** (`dlt-core` / `dlt_parse` rejected; spec §3.1 few dependencies). Zero-copy over the mmap.
- **Location:** `core/src/input/dlt/`, not a `nerka-dlt` crate yet. Extract it into a crate when the `Container` / `Decoder` traits of `sources-and-signals.md` arrive with pcap; that's where a crate boundary pays off.
- **Filtering** by ECU / APID / CTID / level comes from the headers (source-supplied fields + DSL field predicates), never guessed from text. Header-only filters must not decode payloads, and every fast path is tested against the naive per-line evaluator.
- **Display:** a real table (aligned, resizable columns), built into our own log view; **no column sorting** (it would break line numbers, bookmarks and next/previous match, and logs are read in time order). Each row is still one tab-separated text line underneath.
- **Test data:** synthetic only (`writer` module + `gen_dlt`); no real `.dlt` files in the repo.
- **Non-verbose messages:** shown as `[message id] hex` until FIBEX support exists. `mid` is that message id: the key into the FIBEX database that will later decode the payload.
- **Time:** `time` is the logger's storage time (seconds since the epoch, UTC), rendered in local time or UTC, `tmsp` the ECU uptime (0.1 ms).
- **Times: local or UTC (owner, 2026-10-26):** values stay UTC inside; what is shown and typed is **local time by default in the GUI** (as DLT Viewer and Wireshark show it; Settings → Times → Show: Local time / UTC, pref `local_time`), UTC by default in the CLI (`--local-time`; stable output for scripts). One switch, `nerka_core::time::set_local`, covers DLT's `time` column, `format_time` (signals, line window, plot axis, rounded to local hours) and `parse_time`: a date-time without a zone (a plain-text capture, `@time >= "…"`) is read as local time, so text logs show as written either way; a time of day is never converted. The offset at each instant comes from the OS with its DST rules for that date (`localtime_r` on Unix, `SystemTimeToTzSpecificLocalTimeEx` on Windows; no dependency), cached per quarter hour. Changing it reopens the tabs. Cost on a 512 MiB DLT filter that renders every line: 177 ms before, 183–188 ms UTC, 186–208 ms local.
- **MF4 local start time (owner, 2026-10-26, optional):** an MF4 header whose time flag says "local time" (`hd_time_flags` bit 0) is read in this computer's zone (Settings → Times → MF4, pref `mf4_local_time`, default on; CLI `--mf4-utc` turns it off); without the flag the start time is UTC, as the format says. The header's timezone / DST offsets are not used. The full `Timestamp { ns, clock }` model of `sources-and-signals.md` waits until sources are merged or signals arrive.

## Signals (v1 built: core, CLI, GUI)

What a signal is was agreed with the owner on 2026-10-24: `sources-and-signals.md` → "What a signal is". Built (2026-10-24):

- **Core** (`core/src/signal.rs`): a `SignalDef` is a name, a kind (`num`: the capture read as decimal / float / `0x` hex; `enum`: the captured text), an NFD query and the named regex group to take the value from (default: the signal's name). A row carries the value when the whole query matches and the group captured something (from a raw regex or a field regex such as `payload ~ /…/`). A signal can't use other signals. `Signals` is a tab's set, by unique name. Spec line (CLI): `NAME[(GROUP)][:num|enum]=QUERY`.
- **NFD** (owner: the syntax keeps signals apart from source fields): `@speed > 100`, `@gear == D`, `@gear ~ /D|N/`. **Events and states** (owner, 2026-10-24): a row that carries a value is an *event*; the *state* is the value held from an event until the next one (already the new value on the event row; none before the first event; not carried from one file into the next in a view of several). `@x` / `@x.state` is the state, `@x.event` a value received on the row, `@x.changed` an event that changed the state (the first one too); `.event` and `.changed` also stand alone. `Query::with_signals` / `compile_in` resolve them; a row without a value only satisfies `!=` and `!~`; unknown signals and views, and operators that don't fit the kind, are errors with positions. The engine collects a signal's events once per file (`SignalDef::series`, cached with the definition and shared by its copies; `Query::prepare` before a scan), so each row only looks them up (binary search). An event condition that rows without an event fail lends its signal's regex as the prefilter. Fast vs naive path tested as for every engine change, also on a view of several files.
- **CLI:** `--signal SPEC` (global, repeatable): `nerka --signal 'lat=/latency_us=(?<lat>\d+)/' filter '@lat > 9000' app.log`.
- **GUI:** 📈 **Signals** in the toolbar opens a right panel for the active tab: each signal with its kind and its state on the cursor line — `• event` when the line itself carries it, else `↑ N`, the line of the event that set it (click to go there); — before the first event; … while the events are being collected (a background job after a change or load); "error" with the reason on hover when its query doesn't fit the file — ✎ edit, − remove, and a form (name, kind, group, query) to add one. Both boxes (Auto and NFD) and library queries know the tab's signals; editing them re-runs a filter or search that uses `@`. `nerka-gui app.log --signal SPEC` defines them at startup. Signals are per tab and not saved (not in presets, not carried by Move to new window).
- **Benchmark** (1 GiB, release, Windows): existing queries unchanged (`search ERROR` ~29–31 ms, `level >= WARN AND raw ~ /timeout/` ~30 ms; DLT `apid == NAV AND level >= WARN` ~30 ms). One CLI run, the pass that collects the events included: `--signal 'lat=/latency_us=(?<lat>\d+)/'` (2 M events) `@lat > 9000` ~110 ms, `@lat.event > 9000` ~115 ms; a timestamp on every line as the clock, `--signal 't:time=/^(?<t>\S+ \S+)/'` (12 M events) `@t < "00:00:30" AND level >= ERROR` ~0.5 s; DLT `@time < "00:01:00"` ~26 ms (no pass: the source answers). Collecting events: a signal that is only a regex scans for it as a plain regex and captures once per hit without allocating; numbers go straight into arrays (with rayon's `flatten` over `Option`s it took 1.7 s, then 4.5 s).
- **Time** (2026-10-24, owner: time is a signal): kind `time` (values in seconds since the epoch, UTC, `core/src/time.rs`): a capture read as a date-time, a time of day (a day is added when it goes back by more than 12 h, i.e. at midnight) or a number. **Formats (owner, 2026-11-02: it was too strict):** dates `2025-10-17`, `2025/10/17`, `2025.10.17`, `17.10.2025`, compact `20251017T100001`, month names (`17 Oct 2025`, `Oct 17, 2025`, `17-Oct-2025`, Apache's `17/Oct/2025:10:00:01 +0200`, a weekday first, RFC 2822, `Fri Oct 17 10:00:01 2025`); times `10:00:01`, `9:05:01`, `10:00`, a fraction after `.` or `,` (log4j), `AM` / `PM`; zones `Z`, `UTC`, `GMT`, `±hh:mm`, `±hhmm`, `±hh`; plain numbers as seconds, or ms / µs / ns since the epoch when too large for seconds (`core/src/time.rs`, `parse_time`, hand-written: a value per event, the time-signal benchmark is unchanged). Not read, ambiguous (to decide with the owner): dates without a year (BSD syslog `Oct 17 10:00:01`), slashed dates with the year last (`10/17/2025` or `17/10/2025`); and a pure 8-digit number stays seconds, not a compact date. `LogSource::time` gives a source's own time: DLT's storage (receive) time; a tab on such a file gets the built-in **`@time`** (every line an event; `Signals::for_source`, CLI and GUI). NFD compares times with a quoted date-time or time of day (`@time >= "2026-10-17 10:00:01.5"`, `@t < "10:30:00"` compares the time of day). The tab's **clock** (`Clock::of`) is the source's time, else its first `time` signal (its state at each line), else line numbers. Not supported yet: user-given formats, time zones other than in the text or this computer's (local time: "Times: local or UTC").

- **Core** (`core/src/input/dlt/fibex.rs`, `Fibex`): a streaming read (`quick-xml`) of ECUS, FRAMES (`ID_<message id>`, PDU instances in sequence, `MANUFACTURER-EXTENSION`: type, level, APID, CTID, source file / line), PDUS (`ho:DESC` text, signal instances), SIGNALS → CODINGS (base data type, bit length); signals that aren't defined are read by their conventional names (`S_UINT32` …). ## Where state lives

Nothing is stored in the cloud.

- **Nerka:** how text files are split into records (`records`), search histories, prefs, query packs (`packs\`), presets (`presets\`) and kept plots (`plots\`) in `%APPDATA%\nerka\` (Linux: `~/.config/nerka/`); bookmarks as `<log>.nerka-marks` next to the log. Copy those files to move them to another machine.
- **Agent sessions** (Claude Code) are local to the machine they ran on. The project's decisions and state belong in this repo (`CLAUDE.md`, this file, `sources-and-signals.md`, `architecture-analysis.md`), so a new session on any machine starts from the repo.

## Known limitations

- The line index uses 8 bytes per line (≈94 MB per 12 M lines); a block-compressed index is planned.
- No follow/tail mode: if a file is truncated while it is mapped, reads may fault.
- Only UTF-8/ASCII text is handled; invalid bytes are shown as U+FFFD.
- The GUI binary is ~19 MB on Linux. The size on Windows hasn't been measured.
- DLT: only files with storage headers; FIBEX only in the common convention (non-verbose messages; no value tables, no FIBEX 4.x specifics yet); arrays/structs/fixed-point arguments shown as hex; time in UTC only; the message index is built single-threaded (~280 ms per GiB).
