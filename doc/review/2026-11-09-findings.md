## Summary

The new work is sound where it is tested: the gate passes, no reader panics in 3,000 mutated inputs, and the native benchmark numbers are where they were. One wrong-result bug was in the mixed layout (fixed here with a test). The larger theme of this review is **silence**: several places drop or miss data without a word, in the engine (senders past a cap, skipped bytes), in the GUI (a job that panics, an option that isn't one) and in the docs an agent must read (cut off by their own size).

What needs attention:
- **Wrong fields in a mixed view** of captures whose protocols have the same fields (S1, fixed).
- **`net.*` queries miss messages silently** once a capture has more than 65,536 senders, and nothing shows what a reader skipped.
- **`doc/status.md` can't be read in one go by an agent**: the read stops before "Decisions pending with the owner".
- **What the owner met using the GUI** (U1–U7, added after the review): lifecycle labels in the plot, checks that are global and always run, windows that don't see each other's changes, a kept plot changing without Keep.
- **The console can't do what the GUI's newest features do** (several files, merge by time, mixed views), and still has no machine-readable output for its main commands.

## Performance

- **Native paths unchanged:** every text, DLT and pcap query within noise of `baseline/bench-2026-11-08.tsv` (−6 % … +5 %, and `search -v ERROR` +15 % in one of two runs), same match counts. The capture router now looks up a sender per datagram; `big.pcap` `apid == NAV AND level >= WARN` 29.8 → 29.7 ms.
- **The gate's first run showed the definition cases at twice the baseline** (`proto == DLTK AND level >= ERROR` 478 ms against 200). That was this review's own CLI trials running next to it; three reruns on the idle machine gave 204–210 ms. A whole rerun on the idle machine is the new baseline: the definition cases −6 % … +3 %.
- **Checked and dropped:** `Records::line_bytes` reserves 12 KiB per rendered line, because a message's slice runs to the end of its buffer. Reserving 256 bytes changed nothing (`raw ~ /timeout/` on 1 GiB DLT: 274–298 ms before, 283–298 ms after), so it is not a finding.
- **Still the slow spots:** DLT `raw ~` renders every message (296 ms per GiB; 11-07 R14); opening a capture through a definition (4.5 s for 25 M messages, 11-08 R4); mixed parts convert each line through a `String` for `raw` (not measured: the CLI can't open two files, R6).
