## WP-2: say what a reader dropped (R2, R3)

**Problem.** Counters exist and reach no one: `DltFile::skipped_bytes`, `CaptureStats { msg_skipped, file_skipped, senders_not_kept }`. `open_with` drops the stats (`core/src/input/mod.rs:69`, the `.0`). Past 65,536 senders `net.*` has no value, so `net.port == 514` counted 65,536 of 150,000 messages.

**Suggestion.**
- `LogSource::notes(&self) -> Vec<String>` (default empty), or a small `Diagnostics` struct; `Records` keeps its `CaptureStats`. `Concat` and `Merged` join their parts' notes with the file name. Mind ARCH-3: this is method 26, so consider doing it together with a first capability split.
- CLI: `nerka open` prints a `notes:` block; `filter` / `search` print the notes to stderr once (not with `-c` only? decide: stderr never breaks a count on stdout).
- GUI: the status after loading ("Indexed … · 14 bytes skipped"), and the top bar's hover. Wording with the owner (HUX-5).
- The cap itself (**ask first**, the owner set it on 2026-11-08): a sender is the full tuple including the source port, so one host with changing source ports fills the table. Options: (a) key senders by (src, dst, dst port, VLAN) and drop `net.sport` to "no value" only when the table is full; (b) two tables, addresses and ports; (c) keep as is and only report. `Framed` has no spare 16 bits for a source port (40 offset + 19 origin + 4 proto + 1 side).

**Test input** (synthetic; keep as `core/examples/gen_syslog_senders.rs` or a test helper):

```python
import struct, sys
out, count = sys.argv[1], int(sys.argv[2])
with open(out, "wb") as f:
    f.write(struct.pack("<IHHiIII", 0xA1B2C3D4, 2, 4, 0, 0, 0xFFFF, 1))
    for i in range(count):
        msg = b"<11>Oct 17 10:00:01 host app[%d]: timeout %d" % (i, i)
        sport, src = 1024 + (i % 60000), bytes([10, 0, 1 + i // 60000, 1])
        udp = struct.pack(">HHHH", sport, 514, 8 + len(msg), 0) + msg
        ip = struct.pack(">BBHHHBBH", 0x45, 0, 20 + len(udp), 1, 0, 64, 17, 0) + src + bytes([10, 0, 0, 2]) + udp
        frame = b"\x02" * 12 + b"\x08\x00" + ip
        f.write(struct.pack("<IIII", 1760695201 + i // 1000, i % 1000, len(frame), len(frame)))
        f.write(frame)
```

**Done when:** a CLI test opens a DLT file with garbage in the middle and sees the note; a core test with more senders than the cap sees the note (make the cap a parameter for the test, don't write 65,537 datagrams).

## WP-3: one schema map, qualified names (R9; R1's cause)

**Problem.** `Records::View::new` (`proto/mod.rs:308`) and `Concat::new` (`concat.rs:98`) each merge schemas by name and each turn a protocol's cells into `info` / `payload`. A field of the same name and another kind is left out without a word. `FieldId` is a position, valid only in the schema it came from; R1 was a position used in the wrong schema.

**Suggestion.**
- A `SchemaMap` in `core/src/input/` (or `event.rs`): built from the parts' schemas, gives the whole's schema and `fn part_id(part, whole_id) -> Option<FieldId>`. Both callers use it. `mixed_cells` already lives in `Records`; keep one renderer for the mixed line.
- Clashes: follow JSON's precedent (`json.raw`). A name that two parts give different kinds becomes `<proto>.<name>` on each (`dlt.type`, `sens.type`), and the plain name is an error that says so. Needs the grammar comment in `dsl/mod.rs` and parser tests with error positions (CLAUDE.md).
- A conformance test for wrappers (new ARCH-10): for `Concat` (same kind, mapped, mixed, mixed with equal schemas), its `View` parts and `Merged`, every line's every field by **name** equals the part's own value. This would have caught R1 without anyone guessing the case.
- While there: `file` as the shortest suffix that tells the files apart (R15); JSON in `kind_name` (R17).

**Done when:** the two merges are one; the conformance test runs over at least the five combinations; `cargo test -p nerka-core --test ksy_dlt` still passes; benchmark unchanged (the map is consulted per field read: keep the `!mapped` shortcut or measure).

## WP-4: a CLI for scripts and agents (R10, 11-07 R6) — ask first on exit codes

**Problem.** Output is for eyes; discovery needs errors; no match and a match both exit 0 (pinned by `cli/tests/cli.rs::no_match_is_success_with_no_output`).

**Suggestion (the order matters: discovery first).**
- `nerka open --json FILE`: `{"file", "format", "size", "lines", "index_bytes", "columns": [...], "fields": [{"name", "kind", "costly"}], "time": {"first", "last"}, "levels": {"ERROR": n, …}, "protocols": [...], "notes": [...]}`. Time span from `LogSource::time` of the first and last line; level counts are a scan (make them `--stats`-gated if slow on 1 GiB).
- `--json` on `filter`, `search`, `lines`, `marks`: JSON Lines, one object per line: `{"line": n, "file": …, "time": …, "level": …, "raw": …}` and, with `--fields a,b`, those fields typed. Hand-written like `check --json` (no serde: spec §3.1), with the existing `js()`.
- `-m N` / `--max-count`, `-A/-B/-C N` context (context lines marked, as grep's `-` separator, or `"context": true` in JSON).
- Exit status: grep's 0 / 1 / 2 is what scripts expect; while at 0.x a default change is possible, else a flag. The owner chose 0 on purpose once (the test's name says so): ask.
- `nerka help nfd`: the grammar comment of `dsl/mod.rs` as text (include it with `include_str!` from one file so it can't drift), plus three examples per source kind.
- stdin (`-`): the engine maps files; reading stdin into `Bytes::Owned` is enough for text.
- Share the JSON writer and the option set with the future MCP server (Next steps in `status.md`): put them in a module the server can use, not in `main.rs` (1,023 lines already).

**Done when:** `cli/tests/cli.rs` covers each new output; README's CLI section and CLAUDE.md's commands show one example each; `tools/bench.sh` numbers unchanged.

## WP-10: checks per tab, and when they run (U2, U4)

**Problem.** Checks are global: defined, switched on and run for every tab (`App::saved_checks`, `CheckDef::is_on`, `Tab::poll_checks`). The pane's header counts by the overall scope even for a check that is `per` a lifecycle (`ui/src/checks.rs:309`).

**Suggestion.**
- Keep **definitions** global (the library of checks, saved in `<config>/nerka/checks`), make **on / off per tab**: a set of names in `Tab`, like the selection. A new tab starts with none on, or with a default set (ask: a "default on" flag per check, or a preset carrying the set; presets already hold a tab's selection, so they are the natural place).
- The saved `on` flag changes meaning (a default, or gone). That is a format change of the checks file: a step in `bundle::STEPS` and a test on an old file (`doc/bundles.md`).
- When they run: a setting **Run checks: automatically / on request**, and a **Run** button in the pane (always there; with "automatically" it reruns). On request, results of an older run are marked stale when the file, the signals or the definitions changed (`checks_key` already knows).
- U4: for a check with `per`, show and count the lifecycle scopes only. What lies outside every lifecycle becomes a scope of its own ("outside lifecycles") if it has findings, so nothing is hidden and the header's number equals what the rows show. `nerka check` (text and `--json`) must agree with the pane; `CheckResult::scopes[0]` being "overall" is used in `core/src/check.rs:306` and `:317`, in the CLI and in `ui/src/checks.rs:794`, `:815`.
- A check is also a signal (`@name`) other checks, filters and the plot use: switching one off in a tab must give a clear error where it is used ("check 'lost' is off in this tab"), not an unknown signal.

**Done when:** two tabs with different checks on, shown by a headless test; a `per` check with findings only outside lifecycles shows that scope and the same number in the header; the migration test passes.

## WP-11: a kept plot changes only on Keep (U5) — reverses a recorded decision

**Problem.** `ui/src/plots.rs:123` `keep_current` writes the tab's current plot into its kept entry whenever the tab switches plots ("so nothing is lost").

**Suggestion.** Treat a kept plot as a preset: using it copies it into the tab; changes are the tab's draft, marked `*` next to the name (the mark exists for saved plots); **Keep** / **Save** writes it, **Revert** drops the draft. To lose nothing when switching, keep the draft per (tab, plot name) for the session instead of writing it into the entry. Presets (`ui/src/presets.rs`) already work this way ("Update 'name' from this tab"): use the same words.

**Done when:** the test `switching_keeps_each_plot_as_it_was` is rewritten for the new rule (a change without Keep leaves the entry as it was; switching back shows the draft), and `status.md` records the decision.

## WP-12: windows that see each other's changes (U3)

**Problem.** Every `nerka-gui` process loads the configuration once and writes whole files from memory. Windows are processes by design (`ui/src/instance.rs`), so there is no shared state; a later save from a stale window overwrites the other window's change.

**Suggestion, smallest first.**
1. **Settings → Reload configuration** (the owner's fallback): runs `load_prefs`, `load_checks`, `load_saved_signals`, the plots' `load` and the library's load again, then rebuilds each tab's signals (`signals_key = None`) and bumps `checks_gen`.
2. **Reload when the window gains focus** if a config file's modification time changed (`instance::Server::set_focused` is called every frame at `main.rs:3738`; compare mtimes only on the focus edge). No watcher thread, no dependency.
3. **Don't overwrite what changed underneath:** before writing a file, compare its mtime (or a hash) with the one read; if it changed, reload and apply this window's edit to the fresh copy (the edits are small: one check, one signal, one pref).
- Per-tab state that is unsaved (a tab's draft plot, its selection) must survive a reload. Session-only items (`•` presets, kept plots) stay per window: say so in the UI.

**Done when:** a test with two `App`s on one config folder: a check saved by one appears in the other after the reload call, and a save from the second doesn't drop the first's.

## WP-13: query signals with the saved signals' options (U6) — design first

**Problem.** A signal that comes from a query's named group can only get a kind and a scope, per tab. Binding to a lifecycle (`per(ecu1)`), a default (`default(idle)`) and the rest of a signal's spec are only for signals written as their own spec, which can't take a pack query's parameters.

**Questions to settle with the owner.**
- Where the options live: in the pack (`signals: s:enum:per(ecu1):default(idle)`, shared with everyone who has the pack, but `ecu1` is a tab's lifecycle name) or with the tab / preset (an override map like `query_kind`, extended to the whole option set). Likely both: the pack gives defaults, the tab overrides, the preset stores the overrides.
- A parameterised query picked twice with different values gives one group name twice: which signal is which (today: one signal, their OR).

**Suggestion.** One `SignalOptions { kind, scope, per, default }` type in core used by saved signals and query signals alike; the Signals panel's edit form opens for a query signal too, with the query text read-only and a note that it comes from `pack.query(params)`. Pack format: extend the `signals:` attribute compatibly (old values still parse), so no migration step; a preset storing overrides is a format addition (check `doc/bundles.md` on whether an addition needs a step).

## WP-14: pull a needed query into the selection (U7) — scope to be reviewed first

**The owner's idea.** A plot, lifecycle or check needs a signal; a library query defines it; nerka offers to add that query to the selection with the Signal role: Yes / No, and a checkbox to remember the answer.

**What is there.** Lifecycles and checks name library queries directly (`{pack.query param=value}`, resolved by `resolve_lifecycles` / `unresolved()` without the selection). Query signals come from the selection only (`core::query_signals`: Include and Signal nodes). A kept plot stores lane names; if a lane's signal isn't there the lane is empty.

**Scope and limits to review (this is the part the owner asked for).**
- **Finding the query:** a signal name is a regex group's name; several queries, in several packs, may capture a group of that name (today they are one signal, their OR). Offer the list, or only act when exactly one matches?
- **Parameters:** a query with parameters can't be pulled without values. Ask for them, take the tab's current values, or refuse?
- **Saved references:** should a plot / check store *which* query its signal came from (`pack.query` + parameters), so the pull needs no guessing? That changes the plot and check formats (migration step).
- **Lifetime:** is a pulled node removed when nothing needs it any more? Marked as pulled in the Selection pane?
- **Side effects:** the Signal role doesn't filter, but it can colour lines and it costs a pass over the file. Presets replace the selection: does a pulled node survive using a preset?
- **Remembering:** per app (prefs) or per plot / check? "No, remembered" needs a way back (Settings).
- **CLI:** the same rule without a dialog: `--pack` given, a `--check` or `--plot`-like use of `@name` that only a library query defines. Pull silently, or an error that names the query?
- **Alternative that avoids the selection:** let plots, like lifecycles and checks, resolve `{pack.query}` themselves; then nothing has to be pulled, and the selection stays what the user put there. Compare this before building the dialog.

**Done when (for the design step):** a short design note in `doc/` (next to `search-manager.md`) answering the points above, agreed by the owner, before any code.
